# 从 dsh-fish 借鉴的清单（2026-10-30）

阅读 `_research/dsh-fish`（DSH 养成插件，~90 模块 / 1001 测试）后的结论。
每条都标注：它怎么做的 → 我们对应到哪 → 现在能不能改 → 排到什么时候。

---

## 1. 只读记忆体检 —— ✅ 已落地

**它**：`derive.js:consistency()` 算「同一信念在不同阶段的表述相似度均值」，
`novelty()` 算「最近一周新话占比」，设置页点一下就能看到「哪两句对不上、哪些快忘了」。
只读账本、不算分、不写盘。

**我们**：`scripts/memory-check.mjs`（`npm run memory:check`），五项检查：

| 检查 | 对应问题 |
|---|---|
| 规模 + KV 索引体积估算 | P1-4 的 20MB 悬崖，把「到量会炸」变成可观测数字 |
| chunk 缺向量数 | 语义召回静默退化 |
| conversation 超期行 | P1-6 幽灵行，没有 TTL 只增不减 |
| 跨 origin 重复内容 | 同一句话存多份，召回声虚高 |
| importance≤2 且超 30 天 | 「快忘了」的那批，对应它的折叠逻辑 |

首跑结果（2026-10-30）：entries 84 / chunks 87 / 缺向量 0 / 索引占用 0.10%。
**纯只读，冻结期也能跑。**

## 2. 折叠而不是搬走 —— ⏸ Phase 6

**它**（`persona.js:foldOlderBeliefs`）：旧判断不删，折成一行
「…（还有 N 条更早的，你记不清原话了）」，原文仍在事件流里，可 `her_recall` 翻回。

**我们**：`demoteSectionEntries` 把旧条目整段搬进 `archive.md`，core 里什么都不留。
模型对那段时期没有概念，被问反而更容易编。

**改法**：搬走时在 core 原位留一行折叠摘要：
`（2026-09 有 12 条往事已归档，你只记得大概）`。
收益是让「不记得」有据可依，而不是只靠 prompt 硬禁。

**成本**：改记忆格式，必须和 Phase 6 的格式变更一起做（单独改会让老档解析不一致）。

---

## 3. 回忆封顶 —— ⏸ 11-01 解冻后，与 P1-1 一起上

**它**（`recall.js`）：`RECALL_LIMIT = 8`、`RECALL_SNIPPET = 200`，注释写得很直接：

> 翻不到就是翻不到，不给她一整个事件流——那等于把「回忆」变成「读档」。

**我们**：`recallMemoryForChat` 只有全局 4000 字符的 `RECALL_CAP`，没有
「条数 × 每条字数」的双重上限，索引长起来会变成没有结构的流水账。

**改法**：加 `maxItems` + `maxCharsPerItem`，超了按分数截断，末尾标「还有 N 条没展开」。
**改召回路径 → 必须等观察期结束**，和 P1-1 的 deadline 同批。

---

## 4. 唤醒配额按时段摊平 —— ⏸ Phase 6

**它**（`scheduler.js:gapSqueeze / nextWakeAt`）：间隔 ≤ 剩余时长/剩余次数 + 1，且 ≥ 45 分钟。
0.8.0 的更新说明写了原因：以前「第二次可能排在第一次之后一分钟」，额度全挤在最后。

**我们**：`PROACTIVE_ENGINE` 也是 cron + 日配额，但没有摊平，3 次额度可以挤在一小时内。

**改法**：`nextWakeAt()` 加 `minGap = max(45min, 剩余时长/剩余次数)`。纯函数，好测。

---

## 5. 外发前扫描凭据 —— ⏸ 11-01 解冻后（改发送路径）

**它**（`guard.js:screenOutgoing`）：消息发出前拦 cookie / token / `sk-` / Bearer / 长 base64。
原则是「宁可少说一句，也不把家里钥匙贴到评论区」。

**我们**：B 站 cookie 已从 Worker 删除（只在 App），但 Worker 仍会把回复转发到各渠道；
角色若在引用记忆时把一段 token 带出来，目前无人拦。

**改法**：加 `looksLikeSecret()`，接在 outgoing 路径上。
**会改变发送行为**（误判会吞消息），所以排到解冻后，并先加一条纯函数测试。

## 6. 提示词审查清单 —— ✅ 已记录

**它**（`rules.js` 四层）：物理层（代码做不到的事）**一个字都不进提示词**。

> 写「你不可以读设定」等于告诉她"旁边有份设定，很关键"——那是诱因，不是防线。

**我们的用法**：这是审查清单，不是代码改造。

新增 prompt 禁令前先问三句：

1. 这条是**表达风格**（该写进 prompt），还是**系统能力**（该用代码不给入口）？
2. 写了之后，会不会反而提示模型「旁边有个东西」？
3. 有没有配套的断言测试？（我们已经有 `prompt.test.ts`，新规则必须带断言）

反例参考：我们刚加的「不记得就说不记得」属于表达层 —— 正确。
如果哪天想写「你不能读自己的配置」，就该改成代码里不暴露这个接口。

## 不建议借鉴

| 它的做法 | 为什么不适合我们 |
|---|---|
| 事件溯源（events.jsonl 只追加） | 我们是「文档为中心 + D1 派生」，用户要能 `/更正`；只追加等于放弃更正能力 |
| 四层规则 + 三处一致性测试 | 改一条规则要动 `rules.js` + 实现 + 测试三处，维护成本翻倍 |
| 零依赖铁律 | 场景不同：我们是 Worker，工具链本身带依赖 |
| 人格四阶段 | 与我们的产品形态无关 |
