# 11-01 解冻后第一批召回改动（代码已就绪，未部署）

对应 10-30 评审的 P2-5 / P1-1 / P1-5，外加从 dsh-fish 借鉴的「回忆封顶」。
四项都落在召回主干上，观察期内不能上，所以先写好、跑绿、等窗口。

## 改了什么

### 1. 三份复制并成一个入口（P1-5）

新增 `src/memory-engine.ts`，导出 `resolveRecall(env, opts)`。
`chat.ts`（原 102-174）、`openai.ts`（原 559-625）、`webproactive.ts`（原 235-299）
三处 ~60 行的 shadow/next 分支全部删除，改为一次调用。

以前任何召回修复都要改三处，漏一处就是渠道间行为不一致——现在只有一处。

### 2. 门控对所有引擎生效（P2-5）

`shouldRecallMemory` 以前只挡 `shadow`/`next`，legacy 那句"你好"照样触发全量召回。
现在 `resolveRecall` 第一步就做门控，低信号直接返回空，一次 IO 都不发。

### 3. 整条召回带 800ms deadline（P1-1）

`withDeadline()` 包住 legacy 召回，新引擎用**剩余预算**。超时返回空召回——
空召回是合法降级，卡住不是。

注意：超时**不会取消**底层请求（Workers 没有通用取消语义），只是让调用方先走。

### 4. 输出封顶（借鉴 dsh-fish `recall.js`）

`capRecallText()`：最多 8 条、每条 200 字，多出来的折成一行
「（还有 N 条相关记忆没展开）」。

理由是它那句注释：不给她一整个索引，那等于把回忆变成读档。

## 上线后看什么

`engine_metrics` 表里 `ms` 字段：

```sql
SELECT mode, COUNT(*) n, AVG(ms) avg_ms,
       SUM(CASE WHEN ms > 800 THEN 1 ELSE 0 END) over_budget
FROM engine_metrics WHERE kind='memory' AND created_at > <上线时间>
GROUP BY mode;
```

- `over_budget` 占比是 deadline 真正生效的比例；如果长期 > 20%，说明 800ms 太紧
- `avg_ms` 与上线前对比，看是不是整体变快

另外观察：低信号消息的回复是否变得"无记忆感"（门控放开的副作用）。

## 5. 每日归档改用 v4-pro + 思考模式（10-30 追加）

**改动前**：`DISTILL_DEEPSEEK_MODEL` 早就配成了 `deepseek-v4-pro`，但 `deepseekDistill`
的请求体里写死 `thinking: { type: 'disabled' }`——等于用便宜模式跑最重的一天一次任务。

**改动**（`distill.ts`）：

| 项 | 之前 | 现在 |
|---|---|---|
| 每日归档 `distillDay` | thinking disabled，4096 tokens | **thinking enabled，8192 tokens** |
| 其他提炼（摘要、压缩、persona drift） | disabled | 不变（控成本） |
| 空内容报错 | "DeepSeek 返回空内容" | 带上 `finish_reason`，能直接看出是不是被 length 截断 |
| 失败兜底 | 回退 Workers AI | 不变 |

**为什么 max_tokens 要跟着加**：思维链算在 `completion_tokens` 里。4096 很容易被推理吃光，
最后 `content` 是空串、`finish_reason=length`，然后静默回退到小模型——表面上"成功"，
实际当天记忆是用 llama-3b 提炼的。

**成本**：`deepseek-v4-pro` 输出按 27 元/百万 token 计。每天多几千个思考 token，
大约 +¥0.1～0.3/天。上线后对比 `completion_tokens` 的日环比，超过 3 倍就说明思考开得过头了。

**测试**：`src/distill.test.ts` 3 例——归档开思考且 8192、其他提炼仍关闭、截断时回退可用。
