## D1-01 偶发两条自己发送的消息；去掉“正在输入”

### 现象

发送消息后，聊天记录里偶发出现两条相同/近似的用户消息。用户同时要求去掉“大肥鱼 · 正在输入”提示。

### 高概率原因

当前发送链路是“本地 pending + 云端消息”双份状态：

1. `ChatActivity.sendText()` 先插入 `PendingMessageEntity`，显示本地气泡；
2. 请求返回后先 `syncEvents()` 把 D1 的 user/assistant 写进 Room；
3. 再删除 pending。

在这三步之间，后台 5 秒轮询、重试或 `syncEvents()` 自己都可能先把服务端 user 消息插入 Room。pending 用 `pending-<localId>` 作为 key，服务端消息用 `<serverId>` 作为 key，两者没有共同的 `client_message_id` 去重，所以会同时显示。

相关位置：

```text
ds-mobile/.../ChatActivity.kt:412-500  sendText()
ds-mobile/.../ChatActivity.kt:360-410  syncEvents()
ds-mobile/.../ChatActivity.kt:895-920  pending 列表渲染
```

### 修复方案

1. **服务端补 `client_message_id`**
   - `messages` 表增加 `client_message_id`；
   - `/v1/chat/completions` 已接收 `client_message_id`，把 user 消息写入 D1 时一并保存；
   - 增加唯一约束：同一 channel + client_message_id 只允许一条 user 消息。

2. **客户端按 client_message_id 对账**
   - `syncEvents()` 插入服务端消息时，如果该消息的 `client_message_id` 命中当前 pending，直接删 pending，不再同时展示；
   - 删除 pending 和插入服务端消息放在同一个 Room transaction 中，避免中间帧出现两条或空白。

3. **发送期间屏蔽重复触发**
   - 发送按钮、语音发送、文件发送统一加 `sending` 互斥；
   - 同一 `clientMessageId` 重试走幂等，不生成新消息。

4. **去掉“正在输入”**
   - 删除 `TypingBubble` 列表项和 `isTyping` 文案；
   - 只保留必要的发送状态，不显示“大肥鱼 · 正在输入”。

### 验收

- 连续发送 50 条，弱网、切后台、重连各 10 次，不出现重复用户气泡；
- 轮询与发送并发时，任意时刻最多一条自己的消息；
- 聊天记录不再出现“正在输入”。

## D1-02 图片/文档/视频的本地预览与上传顺序

### 现象

发送图片时，App 聊天记录里图片还没显示，AI 回复已经先到。用户希望：

- 选中图片后，缩略图先出现在输入框上方；
- 输入框仍可编辑文字；
- 点击发送后，图片和文字一起进入聊天记录；
- 图片在本机聊天记录完全显示后，再上传云端。

文档、视频同理。

### 当前问题

当前媒体发送是“先上传/先请求，再让消息进入列表”：

```text
选图 → 读取/转换 → 上传/请求 → 服务端入库 → syncEvents → 列表才出现
```

上传和模型请求占了主要时间，所以用户先看到回复，后看到自己的图片。

### 修复方案

采用“本地草稿 + 本地消息 + 后台上传”的乐观链路：

1. **输入框上方附件 tray**
   - 选中附件后只记录本地 `content://` URI、MIME、文件名、大小；
   - 显示缩略图/文件卡片，可删除、可继续编辑文字；
   - 发送前不访问云端。

2. **发送时先落本地消息**
   - 生成 `clientMessageId`；
   - 先把 user 消息和本地附件引用写入 Room；
   - 列表立即显示自己的气泡和本地缩略图。

3. **本地可见后再上传**
   - 图片：本地解码/缩略图确认可显示后，再上传 R2；
   - 文档：先显示文件卡片/解析中状态，再解析并上传；
   - 视频：先显示首帧，再上传；
   - 上传完成后调用 chat，把 `image_keys` / `[视频:key]` / `[文件:...]` 发给模型。

4. **状态机**
   - `local_only → uploading → uploaded → replied → failed`；
   - 失败保留本地消息和附件，可重试，不重复插入新消息。

### 验收

- 飞行模式下选图并发送，本地记录可看到缩略图和失败状态；
- 正常网络下，自己的图片/文件气泡先出现，AI 回复后到；
- 图片在本地记录加载完成前，不发起云端 chat 请求；
- 重试不会产生第二条相同消息。

## D1-03 第一次播放动画卡顿

### 现象

App 每次打开后的第一次动画播放比较卡，之后会好一些。

### 待定位

当前代码里的动态内容主要是 `AnimatedImageDrawable`（GIF/动态 WebP）和消息逐句展示动画。最可能的是：

- 动图首次从网络/R2 拉取并解码；
- 解码在主线程或首帧时进行；
- `MediaCaches` 只有内存缓存，进程重启后缓存丢失；
- 第一次播放时才开始 `ImageDecoder` / 设置 `ImageView`。

相关位置：

```text
ds-mobile/.../ChatActivity.kt:2540-2600  MediaBubble / 动图解码
```

### 修复方案

1. 确认卡顿的具体动画类型（GIF、动态 WebP、B 站帧动画还是消息逐句动画）；
2. 增加 **磁盘缓存**：原图/动图字节 + 首帧缩略图，按 URL/key 哈希存储；
3. 解码放到 `Dispatchers.IO`，主线程只 `setImageDrawable`；
4. 历史加载完成后，在后台预取最近 N 个可见媒体；
5. 首次打开时先显示静态首帧，解码完成后再 `start()` 动画；
6. 用 `FrameMetrics` / Macrobenchmark 记录首帧和首次动画耗时。

### 验收

- 冷启动第一次播放不再明显掉帧；
- 第二次打开同一动画直接命中磁盘缓存；
- 首帧出现时间不晚于当前版本。

## D1-04 B 站分享卡片把链接后面的文字吞进卡片

### 现象

输入：

```text
【《干物妹！大肥鱼》...】 https://b23.tv/89xTGA5大肥鱼快看我刷到了什么
```

“大肥鱼快看我刷到了什么”被解析进卡片，而不是留在卡片外。

### 已定位原因

App 的 B 站 URL 正则：

```kotlin
https?://(?:b23\.tv|(?:www\.)?bilibili\.com)/[^\s，。！？)]+
```

它只排除了空白和部分中文标点，没有排除中文字符。短链接后面直接跟中文时，整段中文会被吞进 URL，导致：

- 预览请求拿到错误 URL；
- 卡片内容异常；
- 链接后的正文没有作为普通文字保留。

相关位置：

```text
ds-mobile/.../ChatActivity.kt:418-439  URL 提取与 outgoing
ds-mobile/.../ChatActivity.kt:2074-2090 biliMetaText
ds-mobile/.../ChatActivity.kt:2359-2366 卡片解析
```

### 修复方案

1. URL token 改为只接受 URL 合法字符，遇到中文/中文标点/空白立即停止；
2. 把一条消息解析成结构化片段：

```text
text: "【标题】 "
url: "https://b23.tv/89xTGA5"
textAfter: "大肥鱼快看我刷到了什么"
```

3. 卡片只渲染 B 站标题/封面/UP 主；
4. `textAfter` 作为普通文本在卡片外单独渲染；
5. 用用户给的这条原文做回归测试。

### 验收

- 卡片内只显示 B 站资料；
- “大肥鱼快看我刷到了什么”显示在卡片外；
- 无空格、紧跟中文、多个链接、链接后带标点都正确。

## D1-05 AI 记忆记错信息

### 现象

用户反馈 AI 记错了信息（见当天截图）。具体错项需要在修复时逐条对照。

### 高概率原因

1. `memory.md` 旧版人物底色里残留过行为规则和旧职业描述；
2. `memory_facts` 是增量 upsert，旧 fact 不一定会随 `memory.md` 更新而自动删除；
3. 记忆提取没有把“工作项目”和“个人项目”严格分开；
4. 用户纠正后没有“覆盖旧事实”的明确路径。

本次已经先修正了已知的：

- 旧职业 `C开发（epoll/timerfd/...）` → 嵌入式开发、工作用 C、当前电源监控器；
- `ds-memory` 明确为个人私下项目；
- 旧 QQ/手机服务器/小米插座状态；
- 旧人物底色里的强制回复规则。

### 修复方案

1. **事实来源与优先级**
   - 用户明确纠正 > 最近对话 > 旧摘要；
   - 每条 fact 保留 `source_message_ids`、`updated_at`、`confidence`；
   - 同一 `fact_key` 新值覆盖旧值，不并存。

2. **提取提示词**
   - 明确区分：工作 / 个人项目 / 设备 / 关系 / 偏好；
   - 对“职业、项目、称呼、设备状态”这类高价值字段，要求带时间与来源；
   - 不允许把模型推测写成用户事实。

3. **纠正入口**
   - 支持用户说“记错了，我是……”直接更新对应 fact；
   - 更新后重新生成受影响 chunk 向量；
   - 在管理端可查看 fact 的来源和更新时间。

4. **回归测试**
   - 用本次错项原句做 fixture；
   - 断言旧 fact 被覆盖、搜索结果只返回新值。

### 验收

- 同一问题连续问 3 次，回答一致；
- 用户纠正后下一轮立即使用新事实；
- 旧事实不再被召回。

## D1-06 AI 称呼不符合“喜欢被叫大人”

### 现象

记忆里已经写了偏好“大人”，但实际回复仍出现“大肥鱼”或其他称呼。

### 已定位原因

- `memory.md` 里还保留“名字=大肥鱼”的身份描述；
- 提示词里也有“你现在的名字是「大肥鱼」”；
- 旧的“AI 只认大肥鱼”规则刚删除，模型仍可能把旧称呼当默认自称；
- App 头部/气泡标签也可能固定显示“大肥鱼”。

### 修复方案

1. 在记忆里增加唯一、明确的偏好字段：

```text
preferred_address=大人
disliked_address=大肥鱼
```

2. 提示词优先级：

```text
用户明确称呼偏好 > preferred_address > 角色默认名
```

3. 检查 App UI 里所有固定显示“大肥鱼”的位置：
   - 头部标题可以保留角色名；
   - 但 AI 自称、回复标签、通知文案应使用偏好称呼；
4. 增加测试：用户叫“大肥鱼”时不应把它当作正确称呼；叫“大人”时应自然接受。

### 验收

- 连续 10 轮不出现 AI 自称“大肥鱼”；
- 被叫“大人”时自然回应；
- 被叫“大肥鱼”时可以纠正，但不装作听不见、不冷处理。

## D1-07 早安/晚安总在 5 的整数倍时间发出

### 现象

早安、晚安以及主动消息实际发送时间总是 `xx:x0` 或 `xx:x5`。

### 已定位原因

`targetMinutesFor()` 本身已经按日期+slot 生成随机分钟，但调度入口是 5 分钟一次的 cron。即使目标是 7:47，也只会在 7:50 的 tick 被检查并发出，所以用户看到的时间永远是 5 的倍数。

相关位置：

```text
ds-memory/src/proactive.ts:16-19   窗口
ds-memory/src/proactive.ts:56-66   随机目标
ds-memory/src/index.ts:1824+       cron 调度
```

### 修复方案

#### 短期（不改架构）

- 把主动消息窗口的 cron 改为每分钟检查 `* * * * *`；
- 每次 tick 只判断“当前分钟是否已到当天目标”；
- 目标时间存 `runtime_state`，避免同一分钟重复发；
- 代价：每天约 1440 次调度，需观察 Worker 调用量。

#### 推荐（与 D1-08 一起）

- 用 Durable Object 的 **alarm** 在精确目标时间触发；
- 每个用户/会话一个调度对象，保存当天的 morning/evening/random 目标；
- 到点后写入现有 proactive queue，App 仍按队列接收；
- 客户端可从云端同步“今日目标时间”仅用于展示/调试，不负责触发。

### 验收

- 连续 20 天，发送时间分布不再集中在 5 分钟整数倍；
- 同一天不重复发送；
- 早晚窗口、静默期、冷却逻辑不变。

## D1-08 Durable Objects 可行性评估

### 当前方案

```text
Worker（无状态）
+ D1（消息/记忆事实）
+ R2（memory.md / 媒体）
+ KV（缓存/设备 token）
+ Cron（主动消息）
+ App 5 秒轮询 + SSE
```

优点：

- 成本低、部署简单；
- D1 适合长期消息和记忆；
- 现有代码和观察体系已经稳定；
- 故障排查路径清晰。

缺点：

- 多实例并发时缺少单会话串行化；
- 重复消息、幂等、typing/presence 需要额外设计；
- cron 只有 5 分钟粒度，主动消息时间不自然；
- 轮询有延迟和无效请求。

### Durable Objects 方案

每个用户/会话一个 DO：

- 单线程串行处理消息，天然避免同一会话并发重复；
- WebSocket 长连接，实时推送、typing、presence；
- `alarm()` 精确到分钟，适合早安/晚安/随机主动消息；
- 强一致的小状态（发送锁、今日目标、最后已读）；
- 仍可用 D1 存长期消息、R2 存媒体、KV 存缓存。

代价：

- 需要处理 DO 迁移、实例生命周期、存储计费；
- WebSocket 连接数、断线重连、鉴权要重新设计；
- 现有 5 秒轮询和 SSE 要双轨一段时间；
- 不是“把 Worker 换个名字”，而是一次会话层重构。

### 建议

**短期不要全量迁移。**

优先级：

1. 先在现有架构修 D1-01（client_message_id 幂等）和 D1-07（随机时间）；
2. 用 DO 做一个 **单用户 PoC**：只负责 WebSocket + alarm + 发送锁；
3. 对比重复率、首字延迟、主动消息时间、成本；
4. 通过后再决定是否把实时会话层迁到 DO，D1/R2 继续作为长期存储。

推荐形态是混合：

```text
DO：实时会话 / 发送串行化 / 精确 alarm
D1：长期消息 / 记忆事实
R2：memory.md / 媒体
KV：缓存 / token
```

不要为了“实时”把全部记忆和长期数据搬进 DO。
