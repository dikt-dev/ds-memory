## D3-01 `[END]` 泄漏与静默结束失效

### 现象

用户发“晚安”类消息后：

- AI 仍然正常回复；
- 回复正文末尾出现 `[END]`；
- App 把 `[END]` 当成正文显示出来；
- 继续发“明天见”，AI 仍然继续回复。

用户预期：

```text
AI 判断应该结束时，什么都不输出，
只输出一个 [END] 空消息；App 不显示任何 AI 气泡。
```

### 实际落库证据

D1 中已经出现多条带标记的 assistant 消息：

```text
ID 1000  2026-10-28 02:51:26
嗯，睡吧。（把手机往枕头边一搁，声音闷闷的）[END]

ID 1002  2026-10-28 02:53:30
（迷迷糊糊又摸了下手机）明天见……本小姐说了晚安就晚安了，别又回一句把本小姐吵醒。（翻个身，声音越来越小）[END]

ID 1012  2026-10-28 04:20:13
（应了一声，翻个身）嗯，晚安……这回真睡了，别又冒出来一句。[END]
```

对应上下文：

```text
02:51:26 user    知道了，晚安
02:51:26 assistant 嗯，睡吧。……[END]
02:53:30 user    祝好梦，明天见
02:53:30 assistant ……[END]
```

### 根因

服务端当前只把“整段内容恰好等于 `[END]`”识别为静默：

```ts
export function isSilentEnd(text: string): boolean {
  return (text || '').trim() === SILENT_END_TOKEN;
}
```

但模型实际输出的是：

```text
正文……[END]
```

因此：

1. `isSilentEnd()` 返回 false；
2. 服务端插入 assistant 消息；
3. App 正常显示整段正文和 `[END]`；
4. 模型看到历史里的 `[END]`，后续更容易继续模仿。

这不是单纯的“提示词没写清楚”，而是**服务端没有兜住模型不按格式输出的情况**。

### 修复原则（已按用户澄清修正）

不是把“正文 + 末尾 `[END]`”当成静默，而是：

```text
AI 判断不回 → 整段只能输出 [END]，不能有正文
AI 有正文   → 就是正常回复，[END] 只作为格式标记剔除
```

### 已处理

1. `isSilentEnd()` 只接受“纯标记”（允许标点/空白），`正文……[END]` 不算静默；
2. 服务端对非静默回复统一剔除 `[END]`，不再显示标记；
3. App `ApiClient` 兜底：剔除标记后为空才视为无回复，有正文则正常显示；
4. 网页流式同样只把“纯标记”视为无回复，正文+标记保留正文；
5. 提示词改为“每轮都判断；不回时整条只能有 [END]，前面不能有任何正文”；
6. D1 中历史带标记的消息已清理为纯正文；
7. App 启动时清理本地 Room 中旧版本留下的 `[END]`；
8. 历史消息压缩时也剔除标记，避免模型继续模仿；
9. 增加回归测试：
   - `[END]`
   - `[END]。`
   - `正文[END]` → 不算静默，正文保留
   - `[END] 但是还有话` → 不算静默
   - 普通文本提到 `[END]` → 不算静默

### 验收

```text
“知道了，晚安” → 无 AI 气泡
“祝好梦，明天见” → 模型自己判断；若它选择回复，则正常显示
“晚安，明天几点叫我” → 必须回复
“我回来了” → 必须回复
任何路径都不显示 [END]
```

实际 API 验证：

```text
“知道了，晚安” → no_reply=true
“我回来了” → 正常回复
“晚安，明天见” → 模型选择回复，正文正常，无 [END]
```

## D3-03 静默结束后的主动消息暂停

当前只实现了“这一轮不回复”，还没有实现：

```text
静默结束 → 记录 closed_at
主动消息检查 closed_at → 暂停
用户再次发言 → 解除
```

风险：

- 用户说“晚安，明天见”后，随机主动消息仍可能在夜里发出；
- 即使 AI 这一轮静默，主动消息也会破坏“结束对话”的语义。

待 D3-01 稳定后一起处理。

## D3-04 随机主动消息连续两天为 0

观察：

```text
2026-10-26 random count = 0
2026-10-27 random count = 0
```

原因已核对：`randomCountFor(dateKey)` 按日期种子抽到 0 条，属于 35% 概率分支，不是代码故障。

当前决定：

- 暂不调整参数；
- 继续观察；
- 如果连续 4 天以上为 0，或抽到 1–2 条但长期被决策分卡住，再评估降低 0 条概率或给随机消息加底分。

## D3-05 历史时间标签泄漏

### 现象

2026-10-28 08:59 的 assistant 消息以：

```text
[10-2808:57]（等了半天屏幕一点动静都没有气笑了）……
```

开头，`[10-2808:57]` 是历史消息时间标签，不是回复内容。

### 根因

- 历史消息注入时使用 `withHistoryTimestamp()` 加 `[MM-DD HH:mm]`；
- App 非流式路径会走 `normalizeAssistantText()`，但 **网页流式路径 `chat.ts` 落库时直接用原始 `text`**；
- SSE 清洗也没有处理时间前缀；
- 模型偶尔会模仿历史标签，导致泄漏。

### 已处理

1. `stripLeadingTimeLabels()` 统一清理 `[10-28 08:57]`、`[10-2808:57]`、`【...】` 等前缀；
2. `scrubAiFlavor()` 先清时间标签，再清洗 AI 味；
3. 网页流式落库改用 `normalizeAssistantText()`；
4. D1 已清理 ID 1027 的泄漏内容；
5. App 启动时清理本地 Room 里的旧时间前缀；
6. 补回归测试。

### 验收

```text
回复正文不以 [MM-DD...] 开头
正常说“10-28”不会被误删
```
