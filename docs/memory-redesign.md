# 记忆系统重构方案（免费额度版）

> 目标：她能记住尽量多的事，同时把每次请求压在 **Cloudflare 免费版 10ms CPU** 以内。
> 前提：保留现有 Worker / D1 / KV / R2 / Workers AI，不引入新服务。

---

## 1. 目标与约束

### 1.1 目标（按优先级）

| 优先级 | 目标 | 可度量 |
|---|---|---|
| P0 | 近期记忆（今天/刚才）不丢 | 探针命中率 ≥ 90% |
| P1 | 具体细节说得出来（不是"一个视频"） | 细节率 ≥ 60% |
| P2 | 长期事实不漂移（换工作、改称呼） | 矛盾率 < 5% |
| P3 | 实体回指（"你那个项目"） | 实体题命中率 ≥ 80% |

### 1.2 硬约束

| 资源 | 免费额度 | 对我们的含义 |
|---|---|---|
| Workers CPU | **10 ms / 请求** | 在线路径不能做重计算 |
| KV 写 | 1,000 / 天 | 请求路径**零 KV 写** |
| KV 读 | 100,000 / 天 | 每轮 1~2 次可以 |
| D1 存储 | 5 GB | 三年数据 ≈ 100 MB |
| D1 行读 | 500 万 / 天 | 每轮 < 300 行 |
| D1 行写 | 10 万 / 天 | 每轮 < 50 行 |
| Workers AI | 10,000 Neuron / 天 | 嵌入只能离线批量 |

> **关键事实**：等待外部大模型的 `fetch` **不消耗 CPU**。免费版限制的是 JS 计算，不是模型调用。

## 3. 总体架构

```
                ┌──────────── 离线（cron，分批，CPU 可控）────────────┐
  消息 ───────► │ 抽取 → mem_log / mem_records / mem_entities         │
                │ 每 10 分钟：重建「记忆快照」→ KV（一次写）           │
                │ 每 10 分钟：处理 50 条记录的向量（分批）             │
                │ 每天 04:00：矛盾消解、话题、衰减                     │
                └──────────────────────┬──────────────────────────────┘
                                       │ KV 快照（≤8KB）
                ┌──────────────────────▼──────────────────────────────┐
  用户消息 ───► │ 在线（≤10ms）：读快照 → 关键词/实体命中 → 拼提示词   │
                │            必要时（"上次/那个"）对 ≤50 候选算余弦     │
                └─────────────────────────────────────────────────────┘
```

**一句话**：离线把所有"算"做完，在线只做"读 + 拼"。

## 4. 数据模型

### 4.1 `mem_log` — 只追加的真相

```sql
CREATE TABLE mem_log (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  at          INTEGER NOT NULL,      -- 真实时间（系统时钟）
  actor       TEXT NOT NULL,         -- him | her | system
  kind        TEXT NOT NULL,         -- message | emotion | relation | state | action
  payload     TEXT NOT NULL,         -- JSON：原话/事件/变化
  source_id   INTEGER,               -- 关联 messages.id
  day         TEXT NOT NULL          -- YYYY-MM-DD，便于按天切片
);
CREATE INDEX idx_log_day ON mem_log(day);
CREATE INDEX idx_log_at  ON mem_log(at);
```

**规则**：永不 UPDATE、永不 DELETE。删记忆 = 派生层标 archived。

### 4.2 `mem_records` — 派生结论（双时间轴）

```sql
CREATE TABLE mem_records (
  id           TEXT PRIMARY KEY,     -- 稳定 hash
  type         TEXT NOT NULL,        -- fact|event|promise|preference|sensitivity|quote|topic
  subject      TEXT NOT NULL,        -- him|her|shared
  text         TEXT NOT NULL,        -- 一句话，主语固定
  entities     TEXT DEFAULT '[]',    -- JSON 数组（mem_entities.id）
  valid_from   INTEGER NOT NULL,     -- 从什么时候成立
  valid_to     INTEGER,              -- 什么时候失效（NULL=仍成立）
  recorded_at  INTEGER NOT NULL,     -- 我们什么时候知道的
  confidence   REAL DEFAULT 0.6,     -- 0.95 他明说 / 0.6 推断 / 0.4 猜测
  salience     REAL DEFAULT 0.5,     -- 重要度
  status       TEXT DEFAULT 'active',-- active|superseded|contradicted|archived
  vec          BLOB,                 -- int8 量化向量（离线算）
  keywords     TEXT DEFAULT '[]',    -- 关键词（离线抽）
  provenance   TEXT DEFAULT '[]',    -- 来自哪几条 mem_log
  use_count    INTEGER DEFAULT 0,
  last_used_at INTEGER
);
CREATE INDEX idx_rec_status ON mem_records(status, type);
CREATE INDEX idx_rec_time   ON mem_records(valid_from);
CREATE INDEX idx_rec_sal    ON mem_records(salience DESC);
```

**双时间轴示例**

| text | valid_from | valid_to | status |
|---|---|---|---|
| 他在 A 公司上班 | 2026-09-01 | 2026-11-05 | superseded |
| 他换到 B 公司了 | 2026-11-05 | NULL | active |

### 4.3 `mem_entities` — 实体与别名

```sql
CREATE TABLE mem_entities (
  id            TEXT PRIMARY KEY,
  type          TEXT NOT NULL,     -- person|thing|project|place
  name          TEXT NOT NULL,
  aliases       TEXT DEFAULT '[]', -- ["Claude","小克"]
  first_seen    INTEGER,
  last_mentioned INTEGER
);
```

### 4.4 `cmid_cache` — 取代 KV 里的 app:cmid:*

```sql
CREATE TABLE cmid_cache (
  client_message_id TEXT PRIMARY KEY,
  content           TEXT,
  user_message_id   INTEGER,
  assistant_message_id INTEGER,
  created_at        INTEGER NOT NULL
);
```

> 这一步是 **F0**，先把请求路径上的 KV 写清掉。

## 5. 记忆快照（核心）

### 5.1 结构（存 KV，key = `mem:snapshot`）

```json
{
  "built_at": 1794040000000,
  "core_facts":   [{"id":"f1","text":"他叫小蓝「大肥鱼」","salience":0.9}],
  "sensitivities":[{"id":"s1","text":"讨厌被叫「废物」"}],
  "ongoing":      [{"id":"p1","text":"答应陪他看那部片，还没看"}],
  "recent_events":[{"id":"e1","at":1794039000000,"text":"他重发二创视频，她说能看全了"}],
  "topics_3d":    [{"day":"2026-11-06","titles":["砂锅粥","大肥鱼外号"]}],
  "entities":     [{"id":"ent1","name":"小克","aliases":["Claude"]}],
  "inverted":     {"二创":["e1"],"砂锅粥":["e9"],"项目":["p2"]}
}
```

**大小控制**：≤8 KB（core 8 条、ongoing 5 条、events 12 条、topics 3 天、inverted ≤300 词）。

### 5.2 重建（cron，每 10 分钟）

```text
1. 读最近 24h 的 mem_records（按 salience 排序）
2. 合并同实体记录（保留最高 salience）
3. 抽关键词建倒排（复用 topKeywords，离线做）
4. 写回 KV（1 次写 / 10 分钟 = 144 次/天 << 1000）
```

## 6. 在线读取路径（预算 10ms）

### 6.1 步骤

```ts
// 1) 读快照（1 次 KV 读）
const snap = await KV.get('mem:snapshot', 'json');            // 0.3ms

// 2) 最近 30 轮原文（1 次 D1）
const history = await loadRecentRounds(env, 30, now);          // 1.0ms

// 3) 关键词命中（纯内存）
const hits = matchInverted(snap.inverted, lastUserText);       // 0.5ms

// 4) 只有在"回忆触发"时才走向量
const deep = /上次|之前|那个|记得|那天/.test(lastUserText);
if (deep && hits.length < 3) {
  const vec = await embed(lastUserText);                        // fetch，CPU≈0
  score(deepCandidates.slice(0, 50), vec);                      // 1.2ms
}

// 5) 拼提示词：稳定前缀命中缓存，只拼尾部
const prefix = await KV.get(`prompt:stable:${dateKey}:${stage}`); // 0.3ms
const system = prefix + renderVolatile(snap, hits);             // 2.5ms
```

### 6.2 CPU 预算

| 步骤 | 目标 |
|---|---:|
| KV 读 ×2（快照 + 稳定前缀） | 0.6 ms |
| D1 读历史 | 1.0 ms |
| 关键词匹配 | 0.5 ms |
| 向量（仅深度召回） | 0~1.2 ms |
| 提示词拼接 | 2.5 ms |
| 序列化/收尾 | 1.0 ms |
| **合计** | **5.6~6.8 ms** |

### 6.3 降级顺序（超时就砍）

```text
1. 砍向量 → 只关键词
2. 砍话题标题（3 行）
3. 砍 recent_events 到 5 条
4. 砍深度召回（只保留实体命中）
```

## 7. 离线流水线（cron 分工）

| cron | 频率 | 做什么 | CPU 预算 |
|---|---|---|---|
| `*/5 * * * *` | 5 分钟 | 抽取最近 20 条消息的 fact/event → D1 | <8ms |
| `*/10 * * * *` | 10 分钟 | 重建快照 → KV（1 写） | <6ms |
| `*/10 * * * *` | 10 分钟 | 处理 50 条记录的向量/合并 | <8ms |
| `0 20 * * *` | 每天 04:00 | 矛盾消解、话题、衰减（分批 200 条） | <9ms |
| `0 4 * * 1` | 每周 | 低 salience + 30 天未用 → archived | <6ms |

> 每次 cron 都只处理一小块。**宁可分 20 次跑完，也不要一次算 1000 条。**

---

## 8. 写入流水线（五条规则）

1. **每轮**：原话入 `mem_log`；抽取 fact/event/quote（宁多勿漏）
2. **同实体合并**：每 10 分钟一次，保留最高 salience，其余 `superseded`
3. **矛盾消解**：新记录 `valid_from` 晚于旧记录且实体相同、语义冲突 → 旧记录 `valid_to = 新 valid_from`、`status = superseded`
4. **用户纠正**："不对，是…" → 旧记录 `contradicted`，新记录 `confidence = 0.95`
5. **遗忘**：低 salience + 30 天未用 → `archived`（不删，只是不再召回）

```text
[系统] 人设 / 规则 / 关系阶段        （稳定前缀，缓存）
[系统] 状态卡（情绪/关系阶段）

       · 你答应陪他看那部片，还没看
       · 前天那个二创，结局是 Claude 被感化
```

**规则**：
- 记忆块**紧贴用户消息**（注意力最强位置）
- 用「你记得…」而不是数据列表
- 空命中就不注入（空着比塞满好）
- 每类限额：fact ≤4、ongoing ≤3、event ≤3、quote ≤2

## 15. 实测结果（2026-11-08 首次测量）

### 15.1 CPU 不是瓶颈

用 `performance.now()` 测「拼提示词」这一段（纯 JS，不含 D1/KV 等待）：

```
cpu_prompt  10 次采样  平均 < 1 ms（低于计时器分辨率）
```

**结论：免费版 10ms CPU 完全够用**，提示词拼装的开销远小于预算。

### 15.2 真正的成本是网络往返

第一次采样（把 `await recentTopicsBlock` 包进了测点）得到 **239 ms**。
拆开看：3 天的主题块要读 3 次 KV，每次往返约 80ms。

```
3 次 KV 读 ≈ 240ms   ← 这是 wall time，不是 CPU
```

**已改**：主题块缓存成单个 key `topics:recent`（10 分钟 TTL），3 次 → 1 次。

### 15.3 由此修正的结论

| 原判断 | 修正后 |
|---|---|
| CPU 10ms 是主要风险 | ❌ CPU 只有 <1ms |
| 需要大量"离线预计算"来省 CPU | 部分需要：省的是**往返次数**，不是 CPU |
| 快照机制（F2）优先 | ✅ 仍然值得做，因为把 3~5 次读压成 1 次 |
| 免费版可能不够 | ✅ 够，而且余量很大 |

### 15.4 下一步优先级（按实测调整）

| 顺序 | 内容 | 收益 |
|---|---|---|
| 1 | 快照机制：所有常驻块合并成 1 个 KV key | 请求准备从 ~5 次往返降到 1 次 |
| 2 | 稳定前缀缓存（日期+阶段） | 少一次组装 |
| 3 | 关键词召回（快照内） | 记忆质量 |
| 4 | 深度召回 | 细节 |

### 15.5 第二轮实测（快照 + 缓存 + 预热）

| 阶段 | 优化前 | 优化后 |
|---|---:|---:|
| 读上下文快照（KV） | — | **5~20 ms** |
| 读齐所有块（旧路径） | ~1,100 ms | 不再走 |
| 快照 KV 读 | 28 ms | **5~20 ms** |
| 拼提示词 | <1 ms | <1 ms |
| **召回** | ~1,500 ms | **~1,500 ms（未解决）** |

召回按阶段采样（recall_samples）：

```
load   5~12 ms      ← 已用 KV 缓存解决
rank   1,330~1,760 ms  ← 真正的瓶颈
embed  87~100 ms
expand 0 ms
```

**结论**：召回慢在 `rankMemoryChunks` 这一段，需要继续在函数内部打子阶段
（关键词打分 / MMR / 向量解码），当前还没有定位到具体是哪一步。

> **更正（2026-11-08 下午）**：上面这个结论是错的。
> `rank` 的累加写在 `selectRecall` 之后，把「一次蒸馏模型往返」记进了排序里。
> 纯 JS 排序（rank_kw / rank_vec / rank_mmr）实测全是 **0 µs**（254 次采样），
> 1.3 s 全部是选择器。现在已经拆成独立的 `select` 段与 `select_ms` 指标。
>
> 更根本的问题在 §24：召回语料就是提示词里已经注入的 memory.md，
> 即便把它优化到 0 ms，产出的内容也只是重复。

### 15.6 KV 额度核算

| 项 | 免费额度 | 本方案用量 |
|---|---|---|
| 读 | 100,000/天 | ~5,000 |
| **写** | **1,000/天** | **~320** |
| 存储 | 1 GB | < 100 KB |

写的主要来源：快照 144 + 话题 144 + 预热标记 24 + chunk 缓存 ~10。
**红线**：别把重建频率提到 1 分钟一次（会变成 2,880/天）。

## 24. 收敛：召回不再重复，三处口径统一（2026-11-08 下午）

### 24.1 发现的根因

原本以为「新旧两套引擎在抢答」，实测不是：**新引擎的语料就是提示词里已经注入的 memory.md**。

```text
memory.md                     4,325 字符
mem:chunks:v1                 31 条，其中 30 条逐字出现在 memory.md 里
早于 60 天的 chunk            0 条
```

所以召回在当时的配置下**不可能带回新信息**，却每条消息：

- 读一次 KV（5~20 ms，可接受）
- 排序几百微秒（可接受）
- **调一次选择器模型（实测 avg 1,306 ms，n=309）** ← 唯一的瓶颈

顺带修正 §15.5 的误判：`rank` 的累加写在 `selectRecall` 之后，把模型往返算成了排序。

### 24.2 本轮改动（6 组）

| 组 | 改动 | 效果 |
|---|---|---|
| 计时 | `select` 从 `rank` 里拆出来；`recall_samples` 加 `select_ms/covered/uncovered/selector_skipped` | 指标不再骗人 |
| 短路 | `resolveRecall({ injectedText })`：候选正文已在本轮注入内容里就不召回；全被覆盖时不调选择器 | 省 1.3 s/条 + 一次模型调用 |
| 快照 | `ctx:snapshot:v2` 存**原始 memo items**（v1 只读兜底）；渠道侧不再自己 format | 网页端不再丢中期记忆与今日摘要 |
| 装配 | 网页端补 `promisesBlock` / `memoryAnswerHint`；App/QQ 改 `buildSystemPromptSplit` | 两渠道行为一致；App 前缀缓存恢复命中 |
| 清理 | `next` 模式跳过 legacy `reindexMemory`；chunk 缓存合成一个函数（memory.md ∪ D1 archive） | 不再每晚重算两套索引 |
| 表 | CPU 采样移到 `engine_cpu`；`schema.sql` 补 4 张运行期建表 + 迁移 027 | 新环境不会静默失效 |

### 24.3 覆盖率短路的规则

```text
isCovered(chunk, injected)
  body = chunk.content.trim()
  body.length < 8                     → 不算覆盖（太短会误杀）
  injected.includes(body)             → 覆盖
  injected.includes(body.slice(0,24)) → 覆盖（容忍提示词侧改写/截断）
```

开关：`RECALL_SKIP_COVERED=off` 一键回退；`RECALL_SELECT_MIN_POOL`（默认 4）控制候选少于多少条时干脆不调选择器。

记忆长到超过 tiered 的 16 KB / core 的 12 KB 上限后，被裁掉的条目自动变成「未覆盖」，召回价值自动回来——不需要额外开关。
