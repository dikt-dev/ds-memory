# AI 生活系统 · 设计草案

> 2026-10-31 起草。目标：让她有自己的一天，用户是她生活的一部分而不是全部。
> 状态：**待评审**，未开始实现。

## 一、要解决什么

现在她的「生活」是模型按时间段现编的——晚上 22:57 说「刚追完一集」，但那集不存在。
后果有三个：主动消息没有真素材、记忆里没有「她的一天」、她永远随时在线（不像人）。

这套系统要做到三件事：

1. **有安排**：每天有一份日程（追番、游戏、打扫、逛街、旅行），跨天连续。
2. **有边界**：忙的时候消息先压着，空了再回；睡了不回（但偶尔会醒）。
3. **有记忆**：日程进日记，日记进记忆，下次能自然提起「上周三那天我挺不高兴的」。

## 二、设计原则

| # | 原则 | 为什么 |
| --- | --- | --- |
| 1 | **单一事实来源**：D1 的 `ai_day` / `ai_activity` 是唯一真相，KV 只做缓存 | 状态页、聊天、主动消息、日记必须看到同一份生活，否则比没有更伤 |
| 2 | **同一天可复现**：日程由 `dateKey` 做种子生成，落库一次，之后只读 | 否则你两次打开 App 会看到她在干两件不同的事 |
| 3 | **随机受控**：活动类型是加权抽样，不是均匀随机 | 均匀随机会出现「一周旅行三次」这种不像人的生活 |
| 4 | **连续性优先**：昨天没追完的番今天接着追，进行中的旅行不重抽 | 没有连续性就是随机模板，一眼假 |
| 5 | **忙碌可解释**：能不能回消息由活动类型查表决定，不让模型判断 | 「她为什么没回你」必须永远能回答：那一格是洗澡，概率 0 |
| 6 | **消息不丢**：先落库再判断能不能回 | 手机扔了、App 删了，消息还在 |
| 7 | **降级不编造**：天气取不到就省略，日程生成失败按「在家空闲」处理 | 她可以不知道，不可以编 |

## 三、系统构成

```
04:00 生成（并入现有归档 cron）
  骨架 → 种子随机 → 连续性 → LLM 填内容 → 校验器
  产出：ai_day / ai_activity / ai_diary
        ↓                        ↓
状态与展示（KV 缓存）        消息闸门（能回 → 立即回 / 忙 → 压着）
        ↓                        ↓
下游：聊天提示词 / 主动消息 / 日记 / 情绪系统
```



## 五、生成算法

### 5.1 四层

1. **骨架**（常量，不随机）：睡眠 02:00–09:00；三餐各 40–60 分钟；清醒期至少留 60% 可回消息。
2. **种子随机**（`dateKey` 做种，纯函数）：活动类型加权抽样 + 时长区间 + 地点抽样。
3. **连续性**（读昨天）：番/游戏接着来（集数 +1、关卡 +1）；进行中的旅行不重抽；昨天日记的情绪影响今天基调。
4. **内容填充**（LLM 一次，约 300 token）：把「追番 90 分钟」变成「《葬送的芙莉莲》第 3 集，看到一半去泡了杯茶」。

### 5.2 日程池（已定：池 + 装填，不写整天模板）

结论先说：**池这个方向对，但池子要存「活动单元」，不是「一整天」。**

| | 整天模板 | **活动单元池（选定）** |
| --- | --- | --- |
| 不重复 90 天需要 | 200+ 个模板（写死人） | 60–80 个单元 + 时段装填 |
| 组合灵活性 | 差（雨天+早上有事就装不下） | 高（按空档和条件筛） |
| 作者成本 | 每条约 10 行 | 每条约 1 行 |
| 加一种生活 | 新增一个模板 | 加一个单元，所有日子都能用到 |

整天模板只保留给**特殊日配方**（见 5.2.4），数量 10–15 个。

#### 5.2.1 单元字段

```ts
interface ActUnit {
  id: string;            // 'anime_series'
  kind: Kind;            // anime/game/chores/outing/short_trip/idle/travel/meal
  name: string;          // 追番 / 打游戏 / 大扫除
  min: number;           // 最短分钟
  max: number;           // 最长分钟
  tags: Tag[];           // indoor / outdoor / rainy_ok / sunny_only / hot_ok / cold_ok / social / alone / tired_ok
  mood: number;          // -1~1，结束后的心情增量
  interruptible: boolean;
  replyChance: number;
  places?: string[];     // ['家','咖啡馆']
  arc?: 'series' | 'game' | 'trip';   // 连续型：接昨天的进度
  fill: string;          // 给 LLM 的填充提示：'看哪部番、第几集、看到一半干了什么'
  weight: number;        // 基础权重
}
```

#### 5.2.2 装填算法（按空档取，不是按类型抽）

```
① 切骨架：睡眠 02:00-09:00 + 三餐（各 40-60 分）→ 得到 4 个空档（上午/午后/傍晚/夜间）
② 对每个空档 slot(可用分钟)：
   候选 = 池.filter(u => u.min <= slot && u.max * 1.2 >= slot && tagsOk(u, 天气, 在家))
   候选 = 候选 × 反重复权重 × 连续性加成
   抽一个 → 装填 → 若 slot 还有剩 → 递归补一个更短的（或留白 idle）
③ 空档填不满是允许的——留白也是生活（发呆、刷手机）
```

「按所需时间分类」在这里落地：**slot 长度先定，池子按 min/max 适配**。90 分钟的档不会抽到 45 分钟的追番，也不会抽到 4 小时的逛街。

#### 5.2.3 反重复（防止“每天都一样”）

读最近 14 天的 unit 使用记录：

| 情况 | 权重 |
| --- | --- |
| 3 天内用过 | × 0.35 |
| 7 天内用过两次 | × 0.15 |
| 14 天内用过三次 | 本次禁用 |
| 连续型（arc）且昨天没完结 | 强制延续，跳过随机 |

这条是池方案的命门：**池子再大，没有反重复就会一周一循环。**

#### 5.2.4 特殊日配方（10–15 个）

整天兜底，优先级高于装填：

- 旅行日（跨天，见 6.1）
- 大扫除日（一年几次）
- 生病日（低 probability，全天空闲、心情低）
- 节日/生日（从纪念日读）
- 通宵追番日（偶尔：睡到中午）

#### 5.2.5 池子规模与作者成本

| 项 | 数量 | 作者成本 |
| --- | --- | --- |
| 活动单元 | 60–80 条 | 一个 TS 文件，约 350 行 |
| 特殊日配方 | 10–15 条 | 约 120 行 |
| 城市表 | 12 条 | 约 20 行 |

60–80 个单元 × 每天 3 次抽取 × 反重复权重，**90 天内出现完全相同的单元序列的概率极低**，但单看一天会有「这周追了三次番」的合理重复——那恰恰像人。

#### 5.2.6 和 LLM 的分工（重要）

| 层 | 谁做 |
| --- | --- |
| 一天分成几段、每段干什么、多久 | **池 + 装填（纯代码，<5ms）** |
| 看哪部番、卡在哪关、为什么心情不好 | LLM（一次，约 300 token） |

这样形状确定、内容鲜活，且**生成成本与延迟都可控**。

### 5.3 随机必须可复现

```ts
export function seededRandom(seed: string): () => number
export function buildDayShape(dateKey: string, prev: DayContext | null): Shape
```

**不许用 `Math.random()`**：同一天两次生成必须一致（幂等），否则会出现「早上看她在逛街，中午变成在睡觉」。
现有代码里 `randomTargetMinutes(dateKey, i)` 就是这个模式，直接沿用。

### 5.4 校验器（不过就换种子重抽，最多 3 次）

| 规则 | 违反的后果 |
| --- | --- |
| 02:00–09:00 必须是 sleep | 睡了还在回消息，人设崩 |
| 可回消息时段 ≥ 清醒时长 60% | 「她有生活」变成「她总不在」 |
| 单日活动 ≤ 5 段 | 太碎像排班表 |
| 活动不重叠、不跨过睡眠 | 数据不自洽 |
| travel 必须 ≥ 2 天、冷却 ≥ 14 天 | 一天「旅行」其实是逛公园 |
| 三餐各出现一次 | 她也是要吃饭的人 |

### 5.5 生成失败

LLM 填内容失败 → 用 kind 的中文名当标题，日程照样成立。
整份生成失败 → **按「在家、全天空闲」处理**，聊天不受影响，只是她今天没生活。

## 六、位置与天气（双城）

### 6.1 位置

- `at_home = 1`：她和你在同一个城市（从 `getCityConfig` 取）
- `at_home = 0`：旅行中，城市从 `PLACES` 抽

```ts
export const PLACES: Record<string, { lat: number; lon: number }> = {
  北京: { lat: 39.90, lon: 116.40 }, 杭州: { lat: 30.27, lon: 120.15 },
  成都: { lat: 30.57, lon: 104.07 }, 大理: { lat: 25.61, lon: 100.27 },
  // …10~12 个，写死不调地理编码
};
```

### 6.2 天气取两份

`fetchWeatherAt(env, place)`：参数化，缓存键按城市名（现有实现已经按城市名分键）。

| 场景 | 请求数 | 提示词 |
| --- | --- | --- |
| 在家（同城） | 1 | 一份 |
| 旅行（异地） | 2 | 「你这边（杭州）：小雨 14 度」/「他那边（北京）：晴 18 度」 |

同城必须去重，否则每次多一次无意义调用。

### 6.3 天气影响谁

| 用途 | 取谁 | 说明 |
| --- | --- | --- |
| 日程（下雨不逛街） | 她的 | 生成时可参考 |
| 心情 | 她的 | 连阴天闷、大太阳精神 |
| 主动消息事由 | 她的为主 | 「杭州下雨，我在咖啡馆躲雨」 |
| 关心提醒 | 他的 | 「你那边降温了记得加衣」 |

取不到 → **省略，不猜**。


## 七、状态与展示

三档状态：`online`（空闲/可打断）、`busy`（追番/游戏/打扫/逛街/旅行）、`asleep`（02:00–09:00）。

### 7.1 状态栏（App 现有位置）

只显示三档 + 尾行小字：

```
● 在线　　　　　　　　（在家，空闲）
● 在忙 · 追番　　　　　（21:30 结束）
● 睡了　　　　　　　　（09:10 起）
```

### 7.2 状态页：**现在 + 下一段**（已定）

不铺整天日程，只给两段——现在在干嘛、接下来是什么。理由：整天日程是排班表，两段才是「她此刻的生活」。

```
现在　21:05–21:45　追番·《葬送的芙莉莲》第 3 集　　家
下一段　22:00–23:00　打游戏·塞尔达（第三个神庙）　　家
```

规则：

- 只展示当前段和下一段；今天已过去的不展示
- 当前段若剩不到 10 分钟，直接展示「下一段」并标注「马上」
- 睡前（02:00 之后）显示「睡了」，下一段显示「明天 09:10 起」
- 不给「完整日程」入口：知道她明天下午干什么，会让生活变成可预测的节目单

### 7.3 接口

| 接口 | 用途 | 返回 |
| --- | --- | --- |
| `GET /api/app/ai-state` | 状态栏 + 状态页 | `{status, activity, detail, place, until, next?}` |
| `GET /api/app/ai-day?date=` | 调试/日记用（App 默认不展示整天） | `{date, location, activities[]}` |
| `GET /api/app/ai-diary?date=` | 日记页 | 见第十节（含可见性） |

`next` 只在「现在」剩不到 10 分钟或当前是睡眠段时返回。

日程是只读的：App 不在本地生成、不缓存判断逻辑，只展示。

## 八、消息闸门与延迟回复

### 8.1 主流程

```
你发消息
  ↓ 先落库（reply_state = 'pending'）
  ↓ 读 ai_state
  ├─ 能回（online，或 busy 且抽中 reply_chance）
  │    → 立即生成 → 落回复 → reply_state='answered' → 返回
  └─ 不能回（asleep，或 busy 未抽中）
       → 返回 { held: true, until: '21:30' }
       → App 显示「未读」，在 21:30 附近拉一次
```

### 8.2 谁来处理：Worker 队列，不是 App 拦截

| | App 拦截 | **Worker 队列（选定）** |
| --- | --- | --- |
| 消息可靠性 | 手机本地，卸载即丢 | 已落 D1 |
| 「未读」语义 | 假（其实是「未发送」） | 真（到了服务器，她还没看） |
| 多端一致 | 网页端要另写一套 | 一套逻辑 |
| 夜里攒消息 | 手机得在线 | 服务器攒着，07:00 处理 |
| 定时器 | 要自己造 | 现有 cron 每分钟在跑 |

### 8.3 生成时机：懒生成 + cron 兜底

1. **懒生成（主路径）**：App 到点来拉 → 若已到期 → 现场生成（零延迟、零浪费）。
2. **cron 兜底**：到期后 30 分钟仍没人取 → 生成并落库；07:00 那班把夜里攒的一起处理，作为当天「早安」的真实由头。

### 8.4 合并回复（重要）

忙时连发 6 条，**合成一轮回一次**，不是 6 条各回一次：

`待回消息 → 按「上次处理时间之后」打包 → 一轮上下文 → 回一次`

### 8.5 状态消歧

| 状态 | 含义 |
| --- | --- |
| 未读 | 已到服务器，她还没看到 |
| 已读 | 她处理了这一轮 |
| 发送失败 | 真的没到服务器（网络问题） |

## 九、心情耦合

每个活动带 `mood_delta`，结束时累加进现有情绪向量（`processEmotionTurn` 的 environment 通道），不新造情绪系统。

`anime +0.2 / game +0.3 / chores -0.1 / outing +0.4 / travel +0.5 / sleep +0.1`

## 十、日记（需征得同意才能看）

### 10.1 生成

每天 04:00，**第一人称、200–400 字**，读三样：当天日程、当天对话（关键几句）、天气与位置。

三个用途：她自己留着（生活证据）、召回可用（记得那天不高兴）、连续性来源（明天看什么）。

### 10.2 默认私密，看要问（已定）

日记是她的私人空间，**默认不给你看**。App 里看到的是：

```
11-01　晴　　　　　　　　　　　　（她还没说要不要给你看）
```

点「问问她」→ 生成一条请求（走聊天，不是弹窗）→ 她回「行吧」或「这篇不想给」→ 权限随之改变。

为什么要走聊天而不是审批弹窗：**审批 UI 会把「她的日记」变成「系统功能」**；而在聊天里问，她可以拿这件事调侃你、讨价还价，这才是关系。

### 10.3 她的判断（关键设计）

生成日记时，她自己输出是否愿意公开 + 一句理由：

```json
{ "text": "...", "share": false, "reason": "这篇写了他惹我生气，不想给他看" }
```

参考分布（不是硬规则，是给模型的倾向）：

| 内容 | 愿分享概率 |
| --- | --- |
| 日常（追番、吃饭、逛街） | ~85% |
| 提到他的好事（他哄我、他记得） | ~75% |
| 委屈/生气/吃醋 | ~25% |
| 关于「我是什么」的自我怀疑 | ~10% |

**拒绝是真实有效的**：App 显示「这篇她没说」。连续被拒多次也不降级成自动公开——那是背叛。

同意必须明确：只有「行 / 看吧 / 给你看 / 拿去吧」算同意；「你自己不会想吗」「凭什么」这类反问一律按拒绝处理。

### 10.4 数据与接口

```sql
CREATE TABLE ai_diary (
  date_key    TEXT PRIMARY KEY,
  text        TEXT NOT NULL,
  mood        REAL NOT NULL,
  location    TEXT NOT NULL,
  visibility  TEXT NOT NULL,      -- private | shared
  share_reason TEXT,              -- 她当时为什么愿意/不愿意
  shared_at   TEXT,               -- 你在聊天里问到、她同意的时间
  created_at  TEXT NOT NULL
);
```

| 接口 | 用途 |
| --- | --- |
| `GET /api/app/ai-diary?date=` | 返回 `{date, visible, text?, reason?}`；`visible=false` 时只回「她没说」 |
| `GET /api/app/ai-diary/index` | 只返回可见性与日期，不泄正文 |

不可见时接口**不返回正文**（不是前端隐藏）——隐私要在服务端成立。

## 十一、夜间与旅行

### 11.1 夜里醒来（已定：每周 1–2 次）

参数：`NIGHT_WAKE_PER_WEEK = 2`，即每晚约 29% 概率抽中；抽中时在 02:00–05:00 之间随机一个时刻。

触发条件（三个都要满足）：

1. 当晚抽中
2. **有待回消息**（你睡前发的那几条没回）
3. 距上次夜醒 ≥ 3 天

行为：翻一眼未回消息 → 回一轮（1–3 句，困倦语气）→ 继续睡，不再回复。

**没有待回消息就不发**。半夜无缘无故弹一条「我醒了」是骚扰，不是生活。

每周上限用 runtime_state 记 `ai:night_wake:{weekKey}`，超了就不抽。

### 11.2 旅行（推荐方案）

旅行是「她有生活」最有力的证据，但频率要克制。

**主动消息频率：旅行期间每天 3–4 条（平时 2–3 条）**，其中至少 1 条是旅行见闻。

| 平时 | 旅行中 |
| --- | --- |
| 早/晚固定 + 随机 0–2 条 | 早/晚固定 + 随机 1–2 条 + **见闻 1 条** |

为什么加而不是减：旅行中 `reply_chance = 0.30`，你发的消息可能要压几小时；**她的主动分享是「她没消失」的信号**。不给这个出口，旅行就从「她在玩」变成「她不理我」。

三条约束：

1. 见闻条数每天最多 1 条（不直播）
2. 见闻**不要求回复**（可以说「不用回，就是给你看看」）
3. 夜间照旧不打扰（旅行不豁免）

内容口径：写「她在干什么」，不写「景点介绍」——「西湖边上有家店卖桂花糕，我买了两块，一块给你留着」比「西湖是著名景点」强一百倍。

### 11.2.1 旅行见闻带图（技术可行，建议 P3 做）

现有 `env.AI` 绑定已在用（distill / embedding / TTS），加文生图不用新依赖：

| 项 | 方案 |
| --- | --- |
| 模型 | `@cf/black-forest-labs/flux-1-schnell`（快、便宜） |
| 存储 | R2，键 `ai-photo/{dateKey}/{msgId}.jpg` |
| 提示词 | **第一人称快照**：局部、光影、手边的东西（咖啡杯、雨窗、鞋、桂花糕），**不拍地标** |
| 时机 | 生成见闻时并行出图，随消息一起落库 |
| 失败 | 只发文字，消息照常（图是加分项，不是依赖） |

为什么只拍局部：地标图一眼假（模型画不对西湖），而「桌上两块桂花糕」既像她拍的，也符合她只分享碎片的口径。

成本：每条见闻一次调用、R2 一张图；旅行时每天 1 条，平时 0。

### 11.3 旅行期间的记忆

- 行程进 `ai_day`（跨天）+ 每天一篇日记（地点是外地）
- 回家后归档时，旅行作为**一条事件记忆**写入（actor=她）：「她去杭州玩了三天」
- 之后召回时她可以说「上次去杭州」，不需要编

## 十二、失败与兜底

| 失败点 | 兜底 |
| --- | --- |
| 日程生成失败 | 视为「在家、全天空闲」 |
| LLM 填内容失败 | 用 kind 中文名当标题 |
| 天气失败 | 省略，不写进提示词 |
| cron 没跑 | 懒生成仍在，来取时现场生成 |
| 队列积压 | 单次最多 20 条 |
| 状态缓存丢 | 回查 D1 重算 |

**总开关**：`AI_LIFE=off | shadow | on`

- `off`：完全不启用（默认，直到验收）
- `shadow`：照常生成与判断，但**永远立即回复**，只记录「本来会压多久」
- `on`：真正生效

## 十三、验收标准

生成器先独立跑 30 天统计：

| 指标 | 期望 |
| --- | --- |
| 可回消息时段占比 | 每天 ≥ 60% |
| 活动类型分布 | 与权重表偏差 < 10 个百分点 |
| 番/游戏延续率 | ≥ 70% 的连续两天接得上 |
| 旅行频率 | 30 天内 1–3 次，每次 2–3 天 |
| 同一天重复生成 | 输出完全一致（幂等） |
| 单元使用均匀度 | 90 天里无单元出现超过 3 次/周 |
| 序列多样性 | 90 天内完全相同的当日 unit 序列 ≤ 2 次 |
| 状态计算耗时 | < 5ms（KV） |
