# AI 生活系统 · 设计草案

> 2026-10-31 起草。目标：让她有自己的一天，用户是她生活的一部分而不是全部。
> 状态：**待评审**，未开始实现。

## 一、要解决什么

现在她的「生活」是模型按时间段现编的——晚上 22:57 说「刚追完一集」，但那集不存在。
后果有三个：主动消息没有真素材、记忆里没有「她的一天」、她永远随时在线（不像人）。

这套系统要做到三件事：

1. **有安排**：每天有一份日程（追番、游戏、打扫、逛街、旅行），跨天连续。
2. **有边界**：忙的时候消息先压着，空了再回；睡了不回（但偶尔会醒）。
3. **有记忆**：日程进日记，日记进记忆，下次能自然提起「上周三那天我挺不高兴的」。

## 二、设计原则

| # | 原则 | 为什么 |
| --- | --- | --- |
| 1 | **单一事实来源**：D1 的 `ai_day` / `ai_activity` 是唯一真相，KV 只做缓存 | 状态页、聊天、主动消息、日记必须看到同一份生活，否则比没有更伤 |
| 2 | **同一天可复现**：日程由 `dateKey` 做种子生成，落库一次，之后只读 | 否则你两次打开 App 会看到她在干两件不同的事 |
| 3 | **随机受控**：活动类型是加权抽样，不是均匀随机 | 均匀随机会出现「一周旅行三次」这种不像人的生活 |
| 4 | **连续性优先**：昨天没追完的番今天接着追，进行中的旅行不重抽 | 没有连续性就是随机模板，一眼假 |
| 5 | **忙碌可解释**：能不能回消息由活动类型查表决定，不让模型判断 | 「她为什么没回你」必须永远能回答：那一格是洗澡，概率 0 |
| 6 | **消息不丢**：先落库再判断能不能回 | 手机扔了、App 删了，消息还在 |
| 7 | **降级不编造**：天气取不到就省略，日程生成失败按「在家空闲」处理 | 她可以不知道，不可以编 |

## 三、系统构成

```
04:00 生成（并入现有归档 cron）
  骨架 → 种子随机 → 连续性 → LLM 填内容 → 校验器
  产出：ai_day / ai_activity / ai_diary
        ↓                        ↓
状态与展示（KV 缓存）        消息闸门（能回 → 立即回 / 忙 → 压着）
        ↓                        ↓
下游：聊天提示词 / 主动消息 / 日记 / 情绪系统
```

## 四、数据模型

```sql
CREATE TABLE ai_day (
  date_key    TEXT PRIMARY KEY,      -- 2026-11-01
  location    TEXT NOT NULL,         -- 北京 / 杭州
  at_home     INTEGER NOT NULL,      -- 1 = 在家（默认城市）
  mood_seed   REAL NOT NULL,         -- 当天基调 -1~1
  plan_json   TEXT NOT NULL,         -- 原始生成结果（便于回查/回滚）
  generated_at TEXT NOT NULL
);

CREATE TABLE ai_activity (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  date_key    TEXT NOT NULL,
  start_min   INTEGER NOT NULL,      -- 当天第几分钟
  end_min     INTEGER NOT NULL,
  kind        TEXT NOT NULL,         -- sleep/anime/game/chores/outing/short_trip/travel/meal/idle
  title       TEXT NOT NULL,         -- 《葬送的芙莉莲》第 3 集
  place       TEXT,                  -- 杭州·西湖 / 家
  interruptible INTEGER NOT NULL,    -- 0/1，由 kind 查表
  reply_chance  REAL NOT NULL,       -- 0~1，忙里偷闲概率
  mood_delta    REAL NOT NULL        -- -1~1，进入情绪向量
);
CREATE INDEX idx_ai_activity_day ON ai_activity(date_key, start_min);

CREATE TABLE ai_diary (
  date_key    TEXT PRIMARY KEY,
  text        TEXT NOT NULL,
  mood        REAL NOT NULL,
  location    TEXT NOT NULL,
  created_at  TEXT NOT NULL
);

ALTER TABLE messages ADD COLUMN reply_state TEXT;  -- pending / answered
CREATE INDEX idx_messages_pending ON messages(reply_state);
```

`ai_state` 放 KV（`ai:state:{dateKey}`，TTL 到次日）：

```json
{ "status": "busy", "activity": "追番", "detail": "《芙莉莲》第 3 集",
  "place": "家", "until": "2026-11-01T21:30:00+08:00", "interruptible": true }
```


## 五、生成算法

### 5.1 四层

1. **骨架**（常量，不随机）：睡眠 02:00–09:00；三餐各 40–60 分钟；清醒期至少留 60% 可回消息。
2. **种子随机**（`dateKey` 做种，纯函数）：活动类型加权抽样 + 时长区间 + 地点抽样。
3. **连续性**（读昨天）：番/游戏接着来（集数 +1、关卡 +1）；进行中的旅行不重抽；昨天日记的情绪影响今天基调。
4. **内容填充**（LLM 一次，约 300 token）：把「追番 90 分钟」变成「《葬送的芙莉莲》第 3 集，看到一半去泡了杯茶」。

### 5.2 类型权重

| kind | 权重 | 时长（分钟） | 可打断 | 回复概率 |
| --- | --- | --- | --- | --- |
| anime | 22% | 45–120 | 是 | 0.25 |
| game | 20% | 60–180 | 是 | 0.25 |
| idle（发呆/刷手机） | 13% | 30–90 | 是 | 0.60 |
| chores | 12% | 40–90 | 是 | 0.35 |
| outing（逛街/咖啡/超市） | 18% | 90–240 | 是 | 0.15 |
| short_trip（电影/公园） | 10% | 120–300 | 是 | 0.20 |
| travel | 3% | 跨天 | 是 | 0.30 |
| sleep | 固定 | 02:00–09:00 | 否 | 0 |
| meal | 固定 | 40–60 | 是 | 0.50 |

旅行附加约束：冷却 14 天，每次 2–3 天，不与上次目的地重复。

### 5.3 随机必须可复现

```ts
export function seededRandom(seed: string): () => number
export function buildDayShape(dateKey: string, prev: DayContext | null): Shape
```

**不许用 `Math.random()`**：同一天两次生成必须一致（幂等），否则会出现「早上看她在逛街，中午变成在睡觉」。
现有代码里 `randomTargetMinutes(dateKey, i)` 就是这个模式，直接沿用。

### 5.4 校验器（不过就换种子重抽，最多 3 次）

| 规则 | 违反的后果 |
| --- | --- |
| 02:00–09:00 必须是 sleep | 睡了还在回消息，人设崩 |
| 可回消息时段 ≥ 清醒时长 60% | 「她有生活」变成「她总不在」 |
| 单日活动 ≤ 5 段 | 太碎像排班表 |
| 活动不重叠、不跨过睡眠 | 数据不自洽 |
| travel 必须 ≥ 2 天、冷却 ≥ 14 天 | 一天「旅行」其实是逛公园 |
| 三餐各出现一次 | 她也是要吃饭的人 |

### 5.5 生成失败

LLM 填内容失败 → 用 kind 的中文名当标题，日程照样成立。
整份生成失败 → **按「在家、全天空闲」处理**，聊天不受影响，只是她今天没生活。

## 六、位置与天气（双城）

### 6.1 位置

- `at_home = 1`：她和你在同一个城市（从 `getCityConfig` 取）
- `at_home = 0`：旅行中，城市从 `PLACES` 抽

```ts
export const PLACES: Record<string, { lat: number; lon: number }> = {
  北京: { lat: 39.90, lon: 116.40 }, 杭州: { lat: 30.27, lon: 120.15 },
  成都: { lat: 30.57, lon: 104.07 }, 大理: { lat: 25.61, lon: 100.27 },
  // …10~12 个，写死不调地理编码
};
```

### 6.2 天气取两份

`fetchWeatherAt(env, place)`：参数化，缓存键按城市名（现有实现已经按城市名分键）。

| 场景 | 请求数 | 提示词 |
| --- | --- | --- |
| 在家（同城） | 1 | 一份 |
| 旅行（异地） | 2 | 「你这边（杭州）：小雨 14 度」/「他那边（北京）：晴 18 度」 |

同城必须去重，否则每次多一次无意义调用。

### 6.3 天气影响谁

| 用途 | 取谁 | 说明 |
| --- | --- | --- |
| 日程（下雨不逛街） | 她的 | 生成时可参考 |
| 心情 | 她的 | 连阴天闷、大太阳精神 |
| 主动消息事由 | 她的为主 | 「杭州下雨，我在咖啡馆躲雨」 |
| 关心提醒 | 他的 | 「你那边降温了记得加衣」 |

取不到 → **省略，不猜**。


## 七、状态与展示

三档状态：`online`（空闲/可打断）、`busy`（追番/游戏/打扫/逛街/旅行）、`asleep`（02:00–09:00）。

状态栏只显示三档；详细活动进状态页（「追番 ·《芙莉莲》第 3 集 · 21:30 结束」）。

App 接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/app/ai-day?date=` | 打开 App 时同步整天日程（幂等、可缓存） |
| `GET /api/app/ai-state` | 状态栏三档 + 当前活动（KV 直读） |
| `GET /api/app/ai-diary?date=` | 日记页 |

日程是只读的：App 不在本地生成、不缓存判断逻辑，只展示。

## 八、消息闸门与延迟回复

### 8.1 主流程

```
你发消息
  ↓ 先落库（reply_state = 'pending'）
  ↓ 读 ai_state
  ├─ 能回（online，或 busy 且抽中 reply_chance）
  │    → 立即生成 → 落回复 → reply_state='answered' → 返回
  └─ 不能回（asleep，或 busy 未抽中）
       → 返回 { held: true, until: '21:30' }
       → App 显示「未读」，在 21:30 附近拉一次
```

### 8.2 谁来处理：Worker 队列，不是 App 拦截

| | App 拦截 | **Worker 队列（选定）** |
| --- | --- | --- |
| 消息可靠性 | 手机本地，卸载即丢 | 已落 D1 |
| 「未读」语义 | 假（其实是「未发送」） | 真（到了服务器，她还没看） |
| 多端一致 | 网页端要另写一套 | 一套逻辑 |
| 夜里攒消息 | 手机得在线 | 服务器攒着，07:00 处理 |
| 定时器 | 要自己造 | 现有 cron 每分钟在跑 |

### 8.3 生成时机：懒生成 + cron 兜底

1. **懒生成（主路径）**：App 到点来拉 → 若已到期 → 现场生成（零延迟、零浪费）。
2. **cron 兜底**：到期后 30 分钟仍没人取 → 生成并落库；07:00 那班把夜里攒的一起处理，作为当天「早安」的真实由头。

### 8.4 合并回复（重要）

忙时连发 6 条，**合成一轮回一次**，不是 6 条各回一次：

`待回消息 → 按「上次处理时间之后」打包 → 一轮上下文 → 回一次`

### 8.5 状态消歧

| 状态 | 含义 |
| --- | --- |
| 未读 | 已到服务器，她还没看到 |
| 已读 | 她处理了这一轮 |
| 发送失败 | 真的没到服务器（网络问题） |

## 九、心情耦合

每个活动带 `mood_delta`，结束时累加进现有情绪向量（`processEmotionTurn` 的 environment 通道），不新造情绪系统。

`anime +0.2 / game +0.3 / chores -0.1 / outing +0.4 / travel +0.5 / sleep +0.1`

## 十、日记

每天 04:00 生成，**第一人称、200–400 字**，读三样东西：当天日程、当天对话（关键几句）、天气与位置。

三个用途：App 可看（她有生活的证据）、召回可用（她记得那天不高兴）、连续性来源（明天看什么）。

## 十一、夜间与旅行

| 场景 | 规则 |
| --- | --- |
| 夜里醒来回消息 | 每周 ≤ 1 次，02:00–05:00 概率触发，回一轮继续睡 |
| 旅行跨天 | 照常生成；reply_chance 0.30；主动消息可拿旅行当由事 |
| 旅行期间被压的消息 | 照常排队，回家后一起回 |

## 十二、失败与兜底

| 失败点 | 兜底 |
| --- | --- |
| 日程生成失败 | 视为「在家、全天空闲」 |
| LLM 填内容失败 | 用 kind 中文名当标题 |
| 天气失败 | 省略，不写进提示词 |
| cron 没跑 | 懒生成仍在，来取时现场生成 |
| 队列积压 | 单次最多 20 条 |
| 状态缓存丢 | 回查 D1 重算 |

**总开关**：`AI_LIFE=off | shadow | on`

- `off`：完全不启用（默认，直到验收）
- `shadow`：照常生成与判断，但**永远立即回复**，只记录「本来会压多久」
- `on`：真正生效

## 十三、验收标准

生成器先独立跑 30 天统计：

| 指标 | 期望 |
| --- | --- |
| 可回消息时段占比 | 每天 ≥ 60% |
| 活动类型分布 | 与权重表偏差 < 10 个百分点 |
| 番/游戏延续率 | ≥ 70% 的连续两天接得上 |
| 旅行频率 | 30 天内 1–3 次，每次 2–3 天 |
| 同一天重复生成 | 输出完全一致（幂等） |
| 状态计算耗时 | < 5ms（KV） |

## 十四、排期

| 阶段 | 内容 | 影响聊天 | 可回滚 |
| --- | --- | --- | --- |
| **P0** | 表 + 生成器 + 校验 + 状态接口 + 心情耦合 | 否 | 删表即可 |
| **P1** | 位置 + 双城天气 + 日记 | 否 | 关开关 |
| **P2** | 闸门 + 队列 + 懒生成 + cron 兜底 + App 未读态 | **是** | `AI_LIFE=off` |
| **P3** | 忙里偷闲、夜里醒来、旅行跨天 | 是 | 同上 |

P0+P1 完成后「她有生活」已经可见；P2 才改变响应行为，单独观察。

## 十五、待定（需要拍板）

1. 状态页展示几段：完整日程，还是「现在 + 下一段」？
2. 日记是否给 App 看并可翻阅历史？（建议：给）
3. 旅行期间多久没消息算正常？主动分享旅行时是否抬高频率？
4. 夜里醒来的频率上限（建议每周 1 次）

## 十六、明确不做

- 不做推送（FCM/厂商），沿用闹钟 + 拉取
- 不做多人（只有你一个用户）
- 不改群聊/QQ（已退役）
- 不做「出门就完全失联」——旅行中仍可回，只是慢
