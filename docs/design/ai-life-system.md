# AI 生活系统 · 设计草案

> 2026-10-31 起草。目标：让她有自己的一天，用户是她生活的一部分而不是全部。
> 状态：**待评审**，未开始实现。

## 一、要解决什么

现在她的「生活」是模型按时间段现编的——晚上 22:57 说「刚追完一集」，但那集不存在。
后果有三个：主动消息没有真素材、记忆里没有「她的一天」、她永远随时在线（不像人）。

这套系统要做到三件事：

1. **有安排**：每天有一份日程（追番、游戏、打扫、逛街、旅行），跨天连续。
2. **有边界**：忙的时候消息先压着，空了再回；睡了不回（但偶尔会醒）。
3. **有记忆**：日程进日记，日记进记忆，下次能自然提起「上周三那天我挺不高兴的」。

## 二、设计原则

| # | 原则 | 为什么 |
| --- | --- | --- |
| 1 | **单一事实来源**：D1 的 `ai_day` / `ai_activity` 是唯一真相，KV 只做缓存 | 状态页、聊天、主动消息、日记必须看到同一份生活，否则比没有更伤 |
| 2 | **同一天可复现**：日程由 `dateKey` 做种子生成，落库一次，之后只读 | 否则你两次打开 App 会看到她在干两件不同的事 |
| 3 | **随机受控**：活动类型是加权抽样，不是均匀随机 | 均匀随机会出现「一周旅行三次」这种不像人的生活 |
| 4 | **连续性优先**：昨天没追完的番今天接着追，进行中的旅行不重抽 | 没有连续性就是随机模板，一眼假 |
| 5 | **忙碌可解释**：能不能回消息由活动类型查表决定，不让模型判断 | 「她为什么没回你」必须永远能回答：那一格是洗澡，概率 0 |
| 6 | **消息不丢**：先落库再判断能不能回 | 手机扔了、App 删了，消息还在 |
| 7 | **降级不编造**：天气取不到就省略，日程生成失败按「在家空闲」处理 | 她可以不知道，不可以编 |

## 三、系统构成

```
04:00 生成（并入现有归档 cron）
  骨架 → 种子随机 → 连续性 → LLM 填内容 → 校验器
  产出：ai_day / ai_activity / ai_diary
        ↓                        ↓
状态与展示（KV 缓存）        消息闸门（能回 → 立即回 / 忙 → 压着）
        ↓                        ↓
下游：聊天提示词 / 主动消息 / 日记 / 情绪系统
```

## 五、生成算法

### 5.1 四层

1. **骨架**（常量，不随机）：睡眠 02:00–09:00；三餐各 40–60 分钟；清醒期至少留 60% 可回消息。
2. **种子随机**（`dateKey` 做种，纯函数）：活动类型加权抽样 + 时长区间 + 地点抽样。
3. **连续性**（读昨天）：番/游戏接着来（集数 +1、关卡 +1）；进行中的旅行不重抽；昨天日记的情绪影响今天基调。
4. **内容填充**（LLM 一次，约 300 token）：把「追番 90 分钟」变成「《葬送的芙莉莲》第 3 集，看到一半去泡了杯茶」。

### 5.2 日程池（已定：池 + 装填，不写整天模板）

结论先说：**池这个方向对，但池子要存「活动单元」，不是「一整天」。**

| | 整天模板 | **活动单元池（选定）** |
| --- | --- | --- |
| 不重复 90 天需要 | 200+ 个模板（写死人） | 60–80 个单元 + 时段装填 |
| 组合灵活性 | 差（雨天+早上有事就装不下） | 高（按空档和条件筛） |
| 作者成本 | 每条约 10 行 | 每条约 1 行 |
| 加一种生活 | 新增一个模板 | 加一个单元，所有日子都能用到 |

整天模板只保留给**特殊日配方**（见 5.2.4），数量 10–15 个。

#### 5.2.1 单元字段

```ts
interface ActUnit {
  id: string;            // 'anime_series'
  kind: Kind;            // anime/game/chores/outing/short_trip/idle/travel/meal
  name: string;          // 追番 / 打游戏 / 大扫除
  min: number;           // 最短分钟
  max: number;           // 最长分钟
  tags: Tag[];           // indoor / outdoor / rainy_ok / sunny_only / hot_ok / cold_ok / social / alone / tired_ok
  mood: number;          // -1~1，结束后的心情增量
  interruptible: boolean;
  replyChance: number;
  places?: string[];     // ['家','咖啡馆']
  arc?: 'series' | 'game' | 'trip';   // 连续型：接昨天的进度
  fill: string;          // 给 LLM 的填充提示：'看哪部番、第几集、看到一半干了什么'
  weight: number;        // 基础权重
}
```

#### 5.2.2 装填算法（按空档取，不是按类型抽）

```
① 切骨架：睡眠 02:00-09:00 + 三餐（各 40-60 分）→ 得到 4 个空档（上午/午后/傍晚/夜间）
② 对每个空档 slot(可用分钟)：
   候选 = 池.filter(u => u.min <= slot && u.max * 1.2 >= slot && tagsOk(u, 天气, 在家))
   候选 = 候选 × 反重复权重 × 连续性加成
   抽一个 → 装填 → 若 slot 还有剩 → 递归补一个更短的（或留白 idle）
③ 空档填不满是允许的——留白也是生活（发呆、刷手机）
```

「按所需时间分类」在这里落地：**slot 长度先定，池子按 min/max 适配**。90 分钟的档不会抽到 45 分钟的追番，也不会抽到 4 小时的逛街。

#### 5.2.3 反重复（防止“每天都一样”）

读最近 14 天的 unit 使用记录：

| 情况 | 权重 |
| --- | --- |
| 3 天内用过 | × 0.35 |
| 7 天内用过两次 | × 0.15 |
| 14 天内用过三次 | 本次禁用 |
| 连续型（arc）且昨天没完结 | 强制延续，跳过随机 |

这条是池方案的命门：**池子再大，没有反重复就会一周一循环。**

#### 5.2.4 特殊日配方（10–15 个）

整天兜底，优先级高于装填：

- 旅行日（跨天，见 6.1）
- 大扫除日（一年几次）
- 生病日（2%/天、30 天冷却；**只能落在在家且当天无旅行**，冲突解决见 activity-pool.md）
- 节日/生日（从纪念日读）
- 通宵追番日（偶尔：睡到中午）

#### 5.2.5 池子规模与作者成本

| 项 | 数量 | 作者成本 |
| --- | --- | --- |
| 活动单元 | 60–80 条 | 一个 TS 文件，约 350 行 |
| 特殊日配方 | 10–15 条 | 约 120 行 |
| 城市表 | 12 条 | 约 20 行 |

60–80 个单元 × 每天 3 次抽取 × 反重复权重，**90 天内出现完全相同的单元序列的概率极低**，但单看一天会有「这周追了三次番」的合理重复——那恰恰像人。

#### 5.2.6 首批池子清单

59 个单元 + 7 个特殊日配方，草稿在 [activity-pool.md](./activity-pool.md)，直接在上面删改。

#### 5.2.7 和 LLM 的分工（重要）

| 层 | 谁做 |
| --- | --- |
| 一天分成几段、每段干什么、多久 | **池 + 装填（纯代码，<5ms）** |
| 看哪部番、卡在哪关、为什么心情不好 | LLM（一次，约 300 token） |

这样形状确定、内容鲜活，且**生成成本与延迟都可控**。

### 5.3 随机必须可复现

```ts
export function seededRandom(seed: string): () => number
export function buildDayShape(dateKey: string, prev: DayContext | null): Shape
```

**不许用 `Math.random()`**：同一天两次生成必须一致（幂等），否则会出现「早上看她在逛街，中午变成在睡觉」。
现有代码里 `randomTargetMinutes(dateKey, i)` 就是这个模式，直接沿用。
### 5.4 作品弧线：番剧/游戏的进度挂在哪（关键）

**问题**：今天看 A 番第 3 集，明天看 B 番第 1 集，后天又回来 A——回来时该播第 4 集，还是第 1 集？

**答案**：进度不能挂在「今天看番」这个动作上，要挂在**作品**上。池子里的 `anime_series` 是「追番」这个行为，不是某一部番。

```sql
CREATE TABLE ai_arc (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  kind        TEXT NOT NULL,      -- series / game / trip
  key         TEXT NOT NULL,      -- '芙莉莲' / '塞尔达' / '杭州-2026-11'
  title       TEXT NOT NULL,
  progress    INTEGER NOT NULL,   -- 看到第几集 / 第几章
  total       INTEGER,            -- 共创，可以没有（连载中）
  status      TEXT NOT NULL,      -- active / paused / finished
  last_at     TEXT NOT NULL,      -- 上次碰它的时间
  note        TEXT                -- '卡在第三个神庙'
);
```

规则：

| 规则 | 说明 |
| --- | --- |
| 进度独立 | 每部作品一条记录，回 A 时读 A 的 `progress` = 3 → 播第 4 集 |
| 同时活跃 ≤ 3 部 | 真实的人也就同时追两三部；超了把「最久没碰」的标 `paused` |
| 抽作品的权重 | 基础 × 新鲜度（越久没碰越想起来的味道，21 天后开始上升）× 是否临近完结 |
| 30 天没碰 | 标 `paused`；下次回来她说「前面有点忘了，回头补了第 2 集」——**这比直接播第 4 集更像人** |
| 完结 | `progress >= total` → `finished`，写一条事件记忆「看完了《X》」，之后可以「重温」 |
| 新作品 | 只在 `active < 3` 时允许开新坑 |

你举的例子走一遍：

```
11-01 追番 → 池子抽到「追番」→ 抽作品：芙莉莲（新建，progress 0）→ 播第 1 集 → progress=1
11-02 追番 → 抽作品：芙莉莲（新鲜度最高）→ 第 2 集 → progress=2
11-03 追番 → 抽作品：进击的巨人（开新坑）→ 第 1 集 → 巨人 progress=1
11-04 追番 → 抽作品：芙莉莲（权重回升）→ **第 3 集**（读的是芙莉莲自己的 progress=2）
```

**游戏同理**：塞尔达的 `progress` 是「已开三个神庙」，换个游戏打一天回来接着第四个，不会回到初始台地。
**旅行同理**：`key` 是「杭州-2026-11」，跨天时读它判断「还在杭州，第 2 天」。

LLM 在这里只做一件事：把 `播放第 3 集` 写成「看到芙莉莲在葬礼上哭那一段，我也跟着鼻子酸了」。**集数不许模型自己数。**



### 5.4.1 番从哪来：静态片单为主，联网为辅（新增）

**能联网找吗？能。** Bangumi / AniList 都有免费 API、不需要 Key，一次请求约 200ms，能拿到真实番名和集数。

但我建议**不要让它成为主路径**：

| | 静态片单（40 部，写死） | 联网查 |
| --- | --- | --- |
| 口味一致性 | 高（她喜欢的类型固定） | 低（每次查到的可能是任意番） |
| 失败风险 | 无 | 网络/接口变更/限流 |
| 幻觉风险 | 无 | 中（标题匹配错、集数错） |
| 剧透风险 | 可控 | 有（简介里带剧情） |
| 成本 | 0 | 200ms + 一次外部依赖 |

**推荐做法**：

1. 写死一个 40 部的片单（真实番剧，含集数），她只从这里挑——口味稳定才像一个人
2. 字段：`title / total / genres / vibe`（healing 治愈 / hype 热血 / mystery 悬疑 / daily 日常 / sad 虐）
3. 挑片按 `vibe` 匹配当天心情（心情低 → 治愈番；精神好 → 热血/悬疑）
4. 追平了不算「完结」，标记为 **「等更新」**——她会说「这季看完了，下一季还得等」。比「完结撒花」更像 2026 年的观众
5. 联网只在片单没有合口味时用：AniList 搜一部，**查到的落库进片单**，下次不再查

**片单草稿已出**：[anime-catalog.md](./anime-catalog.md)，40 部 + 8 部剧场版。

够不够：**片单已按 AniList 核对（2026-11），40 部共 82 季 / 1,361 集。**
有看点番的日子约 22%，一次推进 1 集（通宵 2–4 集），按每月 6–7 天追番算 ≈ **5 年**的量。
原来的 1.5–2 年是把多季番只按第一季算，算少了。所以不需要再补片单。

```ts
/** 一条「季」= 一条可独立推进的弧线（ai_arc 的一行） */
interface SeasonEntry {
  title: string;       // '进击的巨人'
  season: string;      // 'S2' / '最终季' / '续章 上'
  year: number;        // 2017
  episodes: number;    // 12
  vibe: 'healing' | 'hype' | 'mystery' | 'daily' | 'sad';
  status?: 'airing' | 'finished';
}
```

**一季一条进度**：`ai_arc.key` 用 `作品名#季`（如 `进击的巨人#S2`），`cursor_max` 是这一季的集数。
把「进击的巨人 87 集」当成一个数会直接错两次：看到第 25 集时不知道第二季在哪；
追平第一季就以为完结了，而实际还有 5 季。

### 5.4.2 连续性事件：进度、节奏、语义、记忆四道闸（新增）

5.4 解决了「进度挂在作品上」，但光有这个还不够。**连续性事件**（追番、追剧、打游戏、连载小说、学一门乐器）
真正会断的地方有四处，每处要单独设闸，否则单靠一句「接着看第 4 集」的提示，模型照样会退回去。

| 断点 | 症状 | 闸 |
| --- | --- | --- |
| 进度断 | 上次看了第 3 集，这次又从第 1 集开始 | 进度闸：cursor 只属于作品 |
| 节奏断 | 一晚上看了 9 集；或三个月没碰还当作在追 | 节奏闸：谁可以推进、一次推多少 |
| 语义断 | 模型自己数集数，第 4 集写成第 6 集 | 语义闸：集数由代码给，模型只写内容 |
| 记忆断 | 记得看过，但说不上看到哪 | 记忆闸：每集落 event，注入进行中的清单 |

#### 一、进度闸：cursor 挂在作品上，活动只负责「碰它」

```sql
CREATE TABLE ai_arc (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  kind            TEXT NOT NULL,   -- series / game / trip / skill / movie
  key             TEXT NOT NULL,   -- '葬送的芙莉莲' / '塞尔达' / '杭州-2026-11'
  title           TEXT NOT NULL,
  cursor          INTEGER NOT NULL DEFAULT 0,  -- 看到第几集 / 第几章 / 第几天
  cursor_max      INTEGER,         -- 已知总量；连载中可空
  status          TEXT NOT NULL,   -- active / waiting / paused / finished
  mode            TEXT,            -- 空 = 正片；rewatch = 重温（不动 cursor）
  last_at         TEXT NOT NULL,   -- 上次碰它
  last_cursor_at  TEXT,            -- 上次推进 cursor
  next_update_at  TEXT,            -- waiting 时约定「什么时候再看」
  note            TEXT             -- '卡在第三个神庙'
);
```

活动表只记「这一次碰了谁、推到了哪」，不记进度本身：

```sql
-- ai_activity 上新增三列
arc_id         INTEGER,   -- 指向 ai_arc
cursor_before  INTEGER,
cursor_after   INTEGER
```

**为什么这样分**：活动是「今天下午干了什么」，作品是「我看到第几集了」。
删掉今天也不会回退进度；补记昨天也不会重播。

#### 二、节奏闸：一次推进多少由单元决定，不由模型决定

| 单元 | 推进 | 说明 |
| --- | --- | --- |
| `anime_series` | +1 | 一次一集，最正常的速度 |
| `anime_marathon` | +2 ~ +4（种子随机，落库） | 通宵，必须在台词里交代「看了几集」 |
| `anime_rewatch` | 0 | 不动 cursor，只写「重看第 2 遍」 |
| `anime_movie` | 一次性 | `kind='movie'`，结束直接 finished |
| `game` | +1 段 | 关卡/章节，粒度由 arc 自己定 |
| `trip` | +1 天 | 跨天读它判断「还在杭州，第 2 天」 |

硬约束：

- **同一作品每天最多一次活动**（marathon 本身就是一次长活动，不冲突）
- **同一作品同时只允许一条 active 弧线**：S1 没看完不能开 S2（跳季比跳集更假）
- **全局「追番类」单元每天最多 1 次**，避免一天看三部
- **推进量先算再生成**：`cursor_after = clamp(cursor_before + step, 0, cursor_max)`，
  生成阶段拿到的是结果，不是「你随便加」

#### 三、等更新：追平了不等于完结

真实观众追平一部正在连载的番，状态是「等更新」，不是「完结撒花」。

| 情形 | 处理 |
| --- | --- |
| `cursor >= cursor_max` 且片单标记连载中 | `status='waiting'`，`next_update_at` = 今天 + 7 天（片单可覆盖） |
| waiting 期间被抽到 | 权重 ×0.2；台词必须承认「这季看完了，下一季还没来」，**不许编新集** |
| `next_update_at` 到点 | 回 `active`；若片单有第二季则 `cursor_max` 顺延 |
| 片单标记已完结 | `status='finished'`，写 event「看完了《X》」，之后只能 `rewatch` |

#### 四、断档与回归：30 天没碰要「补课」，不要假装没断

- 连续 30 天没碰 → `paused`（同时活跃硬上限仍是 3，超了先压最久没碰的）
- 回来时进**补课模式**：一次活动可 +2 集，台词要交代「隔了半个月，前面有点忘了，回头补了第 2 集」
- 这比「无缝接第 4 集」更像人，也解释了为什么她对剧情有点模糊

#### 五、语义闸：集数由代码给，模型只写这一集发生了什么

给生成器的结构化输入（**只有这些**）：

```ts
{
  title: '葬送的芙莉莲',
  cursorBefore: 2,
  cursorAfter: 3,       // 已 clamp
  isWaiting: false,
  daysSinceLast: 1,
  isCatchUp: false,
  vibe: 'healing',
  recentEvents: ['第 1 集：葬礼那段看哭了', '第 2 集：勇者队伍出发']  // 该 arc 已落库的 event 摘要
}
```

规则：

- 集数由模板拼进句子里，**模型输出里出现「第 N 集」一律以代码给的 N 为准**，出现别的数字直接重写
- 只给本作品已写过的事件摘要，**不给外部简介**——避免剧透，也避免模型「记得」不存在的剧情
- 模型允许写：这一集的一个具体画面、她的反应、她当时在干什么；
  **不允许写**：下一集预告、集数推进、评价整部番的结局

#### 六、记忆闸：连续性靠 event，不靠上下文

| 时机 | 落什么 | importance |
| --- | --- | --- |
| 每集看完 | 「看了《X》第 N 集」+ 一句具体印象 | 2 |
| 追平等更新 | 「《X》本季看完了，等下一季」 | 3 |
| 看完大结局 | 「《X》看完了」 | 4 |
| 弃番（可选，P2） | 「《X》弃了，看不下去」 | 2 |

同时维护一份「进行中的作品」（≤3 条）注入 prompt，让她在**别的场合**也能自然提起：
「昨天那集不是演到…」——这才是连续性的真正体感。

#### 七、验收（写进 §13）

1. 任意 30 天窗口内，同一 `arc_id` 的 `cursor_after` 单调不减，且不存在先看到第 5 集、后看到第 3 集
2. 任意一天，同一 `arc_id` 最多一条活动；追番类单元全局最多一条
3. waiting 状态下不产生「第 N+1 集」内容
4. 连续 30 天未碰的作品出现在 `paused`，回归首条活动带补课说明
5. 每集活动都能查到对应 event，且 event 里的集数与 `cursor_after` 一致

### 5.5 校验器（不过就换种子重抽，最多 3 次）

| 规则 | 违反的后果 |
| --- | --- |
| 02:00–09:00 必须是 sleep | 睡了还在回消息，人设崩 |
| 可回消息时段 ≥ 清醒时长 60% | 「她有生活」变成「她总不在」 |
| 单日活动 ≤ 5 段 | 太碎像排班表 |
| 活动不重叠、不跨过睡眠 | 数据不自洽 |
| travel 必须 ≥ 2 天、冷却 ≥ 14 天 | 一天「旅行」其实是逛公园 |
| 三餐各出现一次 | 她也是要吃饭的人 |

### 5.6 生成失败

LLM 填内容失败 → 用 kind 的中文名当标题，日程照样成立。
整份生成失败 → **按「在家、全天空闲」处理**，聊天不受影响，只是她今天没生活。

### 5.7 社交：朋友怎么设计（新增）

**核心风险**：加朋友很容易滑成「第二个 AI」或「让用户吃醋」。所以先立三条红线：

| 红线 | 说明 |
| --- | --- |
| 1 | 朋友**永远不会出现在对话里**。你只能通过她的话知道他们存在，不能跟他们聊 |
| 2 | 朋友**不建聊天记录、不建人格、不建记忆主体**。他们只是 `ai_people` 里的三行数据 |
| 3 | 朋友不制造「你不如他」的比较。她不会说「我朋友都比你懂我」这种话 |

**三个人，写死：**（填写模板：[friends-template.md](./friends-template.md)，你来定名字和关系）

```sql
CREATE TABLE ai_people (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,          -- 小鹿 / 阿May / 老周
  relation TEXT NOT NULL,      -- 大学室友 / 前同事 / 表姐
  city TEXT,                   -- 同城 / 上海
  looks TEXT,                  -- 样貌一句：能一句话认出来的特征
  note TEXT,                   -- 话很多，爱劝我出门
  created_at TEXT NOT NULL
);
```

| 角色 | 关系 | 作用 |
| --- | --- | --- |
| 小鹿 | 大学室友，同城 | 会拉她出门，是「社交单元」的主要触发者 |
| 阿May | 前同事，异地 | 主要靠发消息/打电话；能提供「别人怎么看这件事」的视角 |
| 表姐 | 亲戚，年长 | 偶尔出现，说些让她烦又没法反驳的话 |

每个朋友多一个 `looks` 字段（**一句话认出来**的特征，不是设定集）——她第一次提到某人时能带一句外貌，之后不重复。写法见 [friends-template.md](./friends-template.md) 四半。

**出现频率**：整周 1–2 次。理由——她生活里有朋友，但朋友不是主线；每周见两次比每天提一嘴更真。

**朋友的作用（这才是价值所在）**：

1. **第三方视角**：她说「小鹿说我最近老看手机」——比她自己说「我一直在等你」更自然，也更有分量
2. **她的生活不围绕你转**：她有事可做、有约可赴，「用户不是她的全部」才有载体
3. **提供话头**：主动消息不必总是「你在干嘛」，可以是「今天跟小鹿吃饭，她说我胖了」

**防跑偏三条**：

- 提到朋友时**不邀请用户参与**（不说「下次带你一起」，那是承诺）
- 朋友**不评价用户**（不说「小鹿说你配不上我」）
- 朋友出现时**不减少对用户的回应**（跟朋友吃饭只是回得慢，不是不回）

- `at_home = 0`：旅行中，城市从 `PLACES` 抽

```ts
export const PLACES: Record<string, { lat: number; lon: number }> = {

  // …10~12 个，写死不调地理编码

```

### 6.2 天气取两份

`fetchWeatherAt(env, place)`：参数化，缓存键按城市名（现有实现已经按城市名分键）。

| --- | --- | --- |
| 在家（同城） | 1 | 一份 |
| 旅行（异地） | 2 | 「你这边（杭州）：小雨 14 度」/「他那边（北京）：晴 18 度」 |

## 七、状态与展示

三档状态：`online`（空闲/可打断）、`busy`（追番/游戏/打扫/逛街/旅行）、`asleep`（02:00–09:00）。

### 7.1 状态栏（App 现有位置）

只显示三档 + 尾行小字：

```
● 在线　　　　　　　　（在家，空闲）
● 在忙 · 追番　　　　　（21:30 结束）
● 睡了　　　　　　　　（09:10 起）
```

### 7.2 状态页：**现在 + 下一段**（已定）

不铺整天日程，只给两段——现在在干嘛、接下来是什么。理由：整天日程是排班表，两段才是「她此刻的生活」。

```
现在　21:05–21:45　追番·《葬送的芙莉莲》第 3 集　　家
下一段　22:00–23:00　打游戏·塞尔达（第三个神庙）　　家
```

规则：

- 只展示当前段和下一段；今天已过去的不展示
- 当前段若剩不到 10 分钟，直接展示「下一段」并标注「马上」
- 睡前（02:00 之后）显示「睡了」，下一段显示「明天 09:10 起」
- 不给「完整日程」入口：知道她明天下午干什么，会让生活变成可预测的节目单

### 7.3 接口

| 接口 | 用途 | 返回 |
| --- | --- | --- |
| `GET /api/app/ai-state` | 状态栏 + 状态页 | `{status, activity, detail, place, until, next?}` |
| `GET /api/app/ai-day?date=` | 调试/日记用（App 默认不展示整天） | `{date, location, activities[]}` |
| `GET /api/app/ai-diary?date=` | 日记页 | 见第十节（含可见性） |

`next` 只在「现在」剩不到 10 分钟或当前是睡眠段时返回。

日程是只读的：App 不在本地生成、不缓存判断逻辑，只展示。

## 八、消息闸门与延迟回复

### 8.1 主流程

```
你发消息
  ↓ 先落库（reply_state = 'pending'）
  ↓ 读 ai_state
  ├─ 能回（online，或 busy 且抽中 reply_chance）
  │    → 立即生成 → 落回复 → reply_state='answered' → 返回
  └─ 不能回（asleep，或 busy 未抽中）
       → 返回 { held: true, until: '21:30' }
       → App 显示「未读」，在 21:30 附近拉一次
```

### 8.2 谁来处理：Worker 队列，不是 App 拦截

| | App 拦截 | **Worker 队列（选定）** |
| --- | --- | --- |
| 消息可靠性 | 手机本地，卸载即丢 | 已落 D1 |
| 「未读」语义 | 假（其实是「未发送」） | 真（到了服务器，她还没看） |
| 多端一致 | 网页端要另写一套 | 一套逻辑 |
| 夜里攒消息 | 手机得在线 | 服务器攒着，07:00 处理 |
| 定时器 | 要自己造 | 现有 cron 每分钟在跑 |

### 8.3 生成时机：懒生成 + cron 兜底

1. **懒生成（主路径）**：App 到点来拉 → 若已到期 → 现场生成（零延迟、零浪费）。
2. **cron 兜底**：到期后 30 分钟仍没人取 → 生成并落库；07:00 那班把夜里攒的一起处理，作为当天「早安」的真实由头。

### 8.4 合并回复（重要）

忙时连发 6 条，**合成一轮回一次**，不是 6 条各回一次：

`待回消息 → 按「上次处理时间之后」打包 → 一轮上下文 → 回一次`

### 8.5 状态消歧

| 状态 | 含义 |
| --- | --- |
| 未读 | 已到服务器，她还没看到 |
| 已读 | 她处理了这一轮 |
| 发送失败 | 真的没到服务器（网络问题） |

## 九、心情与健康

### 9.1 心情

每个活动带 `mood_delta`，结束时累加进现有情绪向量（`processEmotionTurn` 的 environment 通道），不新造情绪系统。

`anime +0.2 / game +0.3 / chores -0.1 / outing +0.4 / travel +0.5 / sleep +0.1`


### 9.2 健康度与康复曲线（已定）

`health` 取值 0–100，默认 100，存 `ai_day.health`。

**曲线**（不是开关，是斜坡）：

```
生病当天      health: 100 → 42      （一次性掉落）
第 2 天       +8   → 50             症状最难受，但开始回升
第 3 天       +14  → 64
第 4 天       +18  → 82
第 5 天       +12  → 94
第 6 天       +6   → 100            痊愈
```

约 5–6 天恢复，前几天最难受。**不是第二天就好**——那会让「生病」变成一句台词。

**健康度影响四件事：**

| 影响 | 规则 |
| --- | --- |
| 日程 | `health < 60` 强制在家，取消出门/旅行/社交，池子只剩室内低强度单元 |
| 回复 | `health < 50` 回得慢、话短、语气软；`health < 30` 可能只回一两个字 |
| 主动消息 | `health < 60` 减到每天 ≤1 条，内容偏「我不太舒服」而非闲聊 |
| 心情 | `health < 70` 时 mood 被拉低，但**不等于心情差**——她可以病着还挺高兴（你关心她） |

**状态栏显示规则**：`health >= 80` 不显示（平时健康是默认值，不需要 HUD）；低于 80 才多一行：

```
● 在忙 · 生病休息中　　　（75）
```

这样健康度只在异常时可见，不会变成常驻血条。

**和旅行的冲突**（你上次提的点）：

- 旅行期间不可生病（`recipe_sick` 生成条件已排除）
- 若在「回家日」生病，旅行照常结束，第二天进入曲线
- 生病期间不抽旅行（`health < 90` 时旅行权重为 0）

**和记忆的关系**：生病作为事件记忆写入（actor=她），康复后可以提「上礼拜病了一场」。


### 9.3 生病时的照顾桥段（已定：可以出现）

生病是少有的「她需要你」的时刻，如果只影响日程就浪费了。但要防止变成索取。

**触发条件（三个都要满足）：**

1. `health < 60` 且 `health >= 30`（太严重时她没力气演）
2. 你在和她说话（不主动半夜发「我不舒服」等人来问）
3. 当天还没用过这个桥段（**每天最多 1 次**）

**她提的要求必须小而具体：**

| 类型 | 例子 |
| --- | --- |
| 想要 | 「给我倒杯水」「想吃粥」 |
| 撒娇 | 「你不哄我我就一直不好」 |
| 撒娇（更近） | 「别走，陪我一会儿」 |
| 嘴硬 | 「没事，我睡一觉就好了」（其实想让你留） |

**给反馈但不给开关：**

- 你顺着接 → 当天 `health +2~4`、`mood +0.2`，她会记一句（进记忆）
- 你没接住 → 她不会立刻翻脸，只是话变少；第二天可能翻旧账（这才是人）
- **不能因为照顾就病好**：康复曲线照走，最多快半天

**防滥用四条：**

- 撒娇不超过 2 轮，第 3 轮要自己收敛（「算了，我自己去」）
- 不拿生病要挟（不说「你不关心我」）
- 病好之后不重复索取
- 不在你明显忙/烦的时候提要求

**语气的刻度**（`health` 越低越短）：

```
health 55  「今天有点烧，不想动」
health 45  「嗯……头有点疼」
health 35  「不想说话，你陪我就行」
health 25  只回一两个字，或者隔很久
```

**和记忆的关系**：被照顾这件事写成事件（actor=她，subject=用户：「他给我倒水、陪我躺着」），康复后可以提「上次病了你也没嫌我烦」。

## 十、日记（需征得同意才能看）

### 10.1 生成

每天 04:00，**第一人称、200–400 字**，读三样：当天日程、当天对话（关键几句）、天气与位置。

三个用途：她自己留着（生活证据）、召回可用（记得那天不高兴）、连续性来源（明天看什么）。

### 10.2 默认私密，看要问（已定）

日记是她的私人空间，**默认不给你看**。App 里看到的是：

```
11-01　晴　　　　　　　　　　　　（她还没说要不要给你看）
```

点「问问她」→ 生成一条请求（走聊天，不是弹窗）→ 她回「行吧」或「这篇不想给」→ 权限随之改变。

为什么要走聊天而不是审批弹窗：**审批 UI 会把「她的日记」变成「系统功能」**；而在聊天里问，她可以拿这件事调侃你、讨价还价，这才是关系。

### 10.3 她的判断（关键设计）

生成日记时，她自己输出是否愿意公开 + 一句理由：

```json
{ "text": "...", "share": false, "reason": "这篇写了他惹我生气，不想给他看" }
```

参考分布（不是硬规则，是给模型的倾向）：

| 内容 | 愿分享概率 |
| --- | --- |
| 日常（追番、吃饭、逛街） | ~85% |
| 提到他的好事（他哄我、他记得） | ~75% |
| 委屈/生气/吃醋 | ~25% |
| 关于「我是什么」的自我怀疑 | ~10% |

**拒绝是真实有效的**：App 显示「这篇她没说」。连续被拒多次也不降级成自动公开——那是背叛。

同意必须明确：只有「行 / 看吧 / 给你看 / 拿去吧」算同意；「你自己不会想吗」「凭什么」这类反问一律按拒绝处理。

### 10.4 数据与接口

```sql
CREATE TABLE ai_diary (
  date_key    TEXT PRIMARY KEY,
  text        TEXT NOT NULL,
  mood        REAL NOT NULL,
  location    TEXT NOT NULL,
  visibility  TEXT NOT NULL,      -- private | shared
  share_reason TEXT,              -- 她当时为什么愿意/不愿意
  shared_at   TEXT,               -- 你在聊天里问到、她同意的时间
  created_at  TEXT NOT NULL
);
```

| 接口 | 用途 |
| --- | --- |
| `GET /api/app/ai-diary?date=` | 返回 `{date, visible, text?, reason?}`；`visible=false` 时只回「她没说」 |
| `GET /api/app/ai-diary/index` | 只返回可见性与日期，不泄正文 |

不可见时接口**不返回正文**（不是前端隐藏）——隐私要在服务端成立。

## 十一、夜间与旅行

### 11.1 夜里醒来（已定：每周 1–2 次）

参数：`NIGHT_WAKE_PER_WEEK = 2`，即每晚约 29% 概率抽中；抽中时在 02:00–05:00 之间随机一个时刻。

触发条件（三个都要满足）：

1. 当晚抽中
2. **有待回消息**（你睡前发的那几条没回）
3. 距上次夜醒 ≥ 3 天

行为：翻一眼未回消息 → 回一轮（1–3 句，困倦语气）→ 继续睡，不再回复。

**没有待回消息就不发**。半夜无缘无故弹一条「我醒了」是骚扰，不是生活。

每周上限用 runtime_state 记 `ai:night_wake:{weekKey}`，超了就不抽。

### 11.2 旅行（推荐方案）

旅行是「她有生活」最有力的证据，但频率要克制。

**主动消息频率：旅行期间每天 3–4 条（平时 2–3 条）**，其中至少 1 条是旅行见闻。

| 平时 | 旅行中 |
| --- | --- |
| 早/晚固定 + 随机 0–2 条 | 早/晚固定 + 随机 1–2 条 + **见闻 1 条** |

为什么加而不是减：旅行中 `reply_chance = 0.30`，你发的消息可能要压几小时；**她的主动分享是「她没消失」的信号**。不给这个出口，旅行就从「她在玩」变成「她不理我」。

三条约束：

1. 见闻条数每天最多 1 条（不直播）
2. 见闻**不要求回复**（可以说「不用回，就是给你看看」）
3. 夜间照旧不打扰（旅行不豁免）

内容口径：写「她在干什么」，不写「景点介绍」——「西湖边上有家店卖桂花糕，我买了两块，一块给你留着」比「西湖是著名景点」强一百倍。

### 11.2.1 旅行见闻带图（技术可行，建议 P3 做）

现有 `env.AI` 绑定已在用（distill / embedding / TTS），加文生图不用新依赖：

| 项 | 方案 |
| --- | --- |
| 模型 | `@cf/black-forest-labs/flux-1-schnell`（快、便宜） |
| 存储 | R2，键 `ai-photo/{dateKey}/{msgId}.jpg` |
| 提示词 | **第一人称快照**：局部、光影、手边的东西（咖啡杯、雨窗、鞋、桂花糕），**不拍地标** |
| 统一滤镜 | 固定风格串，所有图共用：`35mm film, slight grain, warm tungsten light, shallow depth of field, casual snapshot, not professional` |
| 成本 | 每条见闻 1 次调用（约 1–3 秒），R2 一张图 |
| 时机 | 生成见闻时并行出图，随消息一起落库 |
| 失败 | 只发文字，消息照常（图是加分项，不是依赖） |

为什么只拍局部：地标图一眼假（模型画不对西湖），而「桌上两块桂花糕」既像她拍的，也符合她只分享碎片的口径。

成本：每条见闻一次调用、R2 一张图；旅行时每天 1 条，平时 0。

### 11.3 旅行期间的记忆

- 行程进 `ai_day`（跨天）+ 每天一篇日记（地点是外地）
- 回家后归档时，旅行作为**一条事件记忆**写入（actor=她）：「她去杭州玩了三天」
- 之后召回时她可以说「上次去杭州」，不需要编

## 十二、失败与兜底

| 失败点 | 兜底 |
| --- | --- |
| 日程生成失败 | 视为「在家、全天空闲」 |
| LLM 填内容失败 | 用 kind 中文名当标题 |
| 天气失败 | 省略，不写进提示词 |
| cron 没跑 | 懒生成仍在，来取时现场生成 |
| 队列积压 | 单次最多 20 条 |
| 状态缓存丢 | 回查 D1 重算 |

**总开关**：`AI_LIFE=off | shadow | on`

- `off`：完全不启用（默认，直到验收）
- `shadow`：照常生成与判断，但**永远立即回复**，只记录「本来会压多久」
- `on`：真正生效

## 十三、验收标准

生成器先独立跑 30 天统计：

| 指标 | 期望 |
| --- | --- |
| 可回消息时段占比 | 每天 ≥ 60% |
| 活动类型分布 | 与权重表偏差 < 10 个百分点 |
| 番/游戏延续率 | ≥ 70% 的连续两天接得上 |
| 旅行频率 | 30 天内 1–3 次，每次 2–3 天 |
| 同一天重复生成 | 输出完全一致（幂等） |
| 单元使用均匀度 | 90 天里无单元出现超过 3 次/周 |
| 序列多样性 | 90 天内完全相同的当日 unit 序列 ≤ 2 次 |
| 朋友提及频率 | 每周 1–2 次，且从不邀请用户参与 |
| 康复曲线 | 生病后第 6 天回到 100，期间日程/回复/主动消息按 9.2 降级 |
| 状态计算耗时 | < 5ms（KV） |
