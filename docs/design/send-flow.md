# 消息发送时序：解析、显示、已读、开口

> 2026-11-01。目标：**她看到的必须是解析完的整条消息**，界面上不出现"卡片后补"的跳动，
> 已读只在她真的收到之后才亮。

## 一、现在是什么样（代码事实）

| 步 | 代码位置 | 行为 | 问题 |
|---|---|---|---|
| 1 | `ChatActivity.sendText` 508 | 立刻插入 pending 气泡（纯文字），状态"等待回复…" | 用户看到的是**未解析**的裸文字 |
| 2 | 542–557 | 才去解析 B 站/网页 | 卡片信息晚于气泡到达 |
| 3 | 544 | `api.biliPreview` 的结果**没写进** `MediaCaches` | 真正的卡片渲染时（`BiliCard` 1602）缓存未命中，再拉一次：标题先显示"哔哩哔哩视频"，封面后到 |
| 4 | 632–638 | 带媒体时发送前停 `MEDIA_SETTLE_MS = 1500` | 这段时间界面无变化，看着像卡住 |
| 5 | 666–668 | 回复到了才 `syncEvents` 并删掉 pending | 气泡从"纯文字"换成"带卡片"，就是那次跳动的来源 |
| 6 | `ChatUi` READ_HOLD_MS 1500 | 已读亮后停 1.5s 再逐句 | 与第 4 步叠加：媒体消息总共要等 3 秒 |

**关键结论**：跳动有两处——① pending 气泡不含卡片，② 卡片首次渲染时缓存冷。
真正"发出去"的时刻本来就是解析之后（`api.chat` 在 647 行，解析之后），所以
**她的视角没问题，是用户视角的气泡演错了顺序**。

## 二、三个方案

| | A. 解析完才显示（你最初的想法） | B. 立刻显示 + 骨架 | C. 立刻显示 + 原地填充（推荐） |
|---|---|---|---|
| 点发送后 0ms | 什么都不出现 | 气泡出现，卡片位是灰色骨架"正在读取…" | 气泡出现，文字已可见，卡片位是骨架 |
| 解析完成 | 气泡整条出现 | 骨架原地换成封面/标题 | 骨架原地换成封面/标题 |
| 何时真正发送 | 解析后 | 解析后 | 解析后 |
| 纯文字消息 | 有 0–1 次网络往返的空白 | 无差别 | 无差别 |
| **B 站长视频**（抽帧约 4s） | **空白 4 秒**，像没发出去 | 正常 | 正常 |
| 布局跳动 | 无（一次性出现） | 无（骨架预留高度） | 无 |
| 实现量 | 小 | 中 | 小~中 |

选 A 的风险很具体：`BiliFrames.loadAiFrames` 抽宫格 + 规划轮 + 细节帧，长视频
实测能到 3–5 秒。这 5 秒里界面上什么都没有，用户第一反应是"没点上"，会重复发送。

## 三、推荐的时序（方案 C）

```
0ms      点发送
         输入框清空；气泡立刻出现（文字 + 卡片骨架）
         状态行：「正在读取链接…」
~0.3-1.5s 解析回来：封面/标题原地填入（骨架尺寸不变，无位移）
          同时把结果写进 MediaCaches（后续渲染直接命中，不再二次加载）
         （带短视频/长视频时）状态行：「正看着你发的…」，抽帧 + 规划轮在这里跑完
         解析/抽帧完成 → 才调用 api.chat（她收到的就是解析完的那条）
         状态行：「等待回复…」
回复到达   已读 亮（此时她的消息确实已经在手机上）
+1.5s     她的消息逐句展开
```

要点：

1. **界面先给"我说了"的确认，再给"解析好了"的确认**。文字是用户自己打的，本来
   就是真的，立刻显示不撒谎；卡片是外部数据，骨架就是在说"还没好"。
2. **发送（api.chat）依然在解析之后**，所以她的输入永远是完整的——你的原始要求不变。
3. **已读只在回复到手机后亮**（已改好：`newer?.role == "assistant"`）。
4. **已读到开口 1.5s**：她说"收到 → 读了 → 停一下 → 才开口"。
   但媒体消息发送前已经停过 1.5s，两个 1.5s 叠加会显得拖——
   建议媒体消息的开口停顿降到 **0.6s**，纯文字保持 1.5s。

## 四、要改的地方

| # | 文件 | 改动 | 风险 |
|---|---|---|---|
| 1 | `ChatActivity.sendText` | 解析结果 `MediaCaches.putBiliPreview/putWebPreview` | 无 |
| 2 | `ChatActivity.sendText` | 解析完成后再 `dao.updatePendingContent(...)`（或内存 map）以便气泡带卡片 | 低 |
| 3 | `ChatUi.PendingMessageRow` 1323 | 增加可选 `card` 参数：有链接就渲染 `BiliCard`/`WebCard`（缓存已热） | 低 |
| 4 | `ChatUi.PendingMessageRow` | 卡片位置骨架：`surfaceMuted` 圆角块 + "正在读取链接…"，尺寸与卡片一致 | 低 |
| 5 | `ChatActivity.sendText` 632 | `MEDIA_SETTLE_MS` 从 1500 → 0（停顿改由"已读到开口"承担） | 低 |
| 6 | `ChatUi` READ_HOLD_MS | 参数化：纯文字 1500 / 带媒体 600 | 无 |

DB 不用改：不清空 `pending.content` 也能做——卡片靠 `pendingCards[pendingId]` 这个
内存 map 传给 `PendingMessageRow`，pending 被删时一起清掉。

## 五、边界

| 情况 | 处理 |
|---|---|
| 解析失败（404/超时） | 不显示卡片，按纯文字发送；状态行「链接没读出来，先按文字发」 |
| 断网 | 气泡立刻变「待重试」（已有 `reconcilePending`），卡片骨架撤回 |
| 发送失败但服务端已落库 | 已有对账逻辑（`reconcilePending`），不动 |
| 多条链接 | 仍只解析第一条（现状），其余按文字 |
| 抽帧失败 | 不影响发送，只是她没看到画面（现有 `getOrDefault(emptyList())`） |

## 七、已落地（2026-11-01，release 包实测）

方案 C 实现完毕，真机（Pixel，release/R8）跑了一条 B 站链接 + 一条纯文字，逐帧截图确认：

| 时刻 | 界面 |
|---|---|
| +0.4s | 气泡出现：文字 + 骨架「正在读取链接…」，气泡上方标「发送中」 |
| +1.6s | 骨架仍在（b23 短链要跳转，比直链慢） |
| +4.1s | 封面/标题/UP 主/时长原地填入，尺寸不跳；气泡仍是「发送中」 |
| 回复到达前 | **「已发送」+ 单个 ✓**（服务端已落库、她还没开口） |
| 回复到达 | **「已读」+ 双 ✓** |
| +1.5s | 她的消息先显示「●●●」，再逐句展开 |

纯文字那条：1.7s「发送中」→ 2.6s「已发送」→ 4.7s「已读」+ 打字点 → 6.2s 开口。

### 实现了什么

| 改动 | 位置 |
|---|---|
| 解析结果写进 `MediaCaches` | `ChatActivity.sendText` |
| pending 气泡渲染真卡片（骨架 → 原地填充） | `ChatUi.PendingMessageRow` + `LinkSkeleton` |
| 去掉发送前 1.5s 固定停顿 | `ChatActivity`（`MEDIA_SETTLE_MS` 删除） |
| 三档回执 发送中 / 已发送 / 已读 | `ChatUi.Receipt` |
| 已读到开口停顿整条生效（原来只对分段回复） | `ChatUi.MessageItem` `holdMs`（纯文字 1500 / 带图 600） |
| 等待期间 0.7s 对账，pending 换成正身 | `ChatActivity.sendText` 里的 `watcher` |
