# memory.md 的未来角色：四种定位的利弊

> 现状：memory.md 是唯一的"人物档案"——人物底色、称呼关系、雷区禁忌、长期偏好全在里面，
> 每轮聊天都整份注入。它同时承担了四件事：**人设**、**事实库**、**习惯偏好**、**近况摘要**。
> 一体承担的直接后果是：想改任何一件小事，都得动同一份文件；每轮注入的 token 也只涨不落。

跑了一段时间后的实测约束（决定了哪些方案可行）：

- 现在整份约 12.7 KB / 4k+ token，每轮注入 → 一天 60 轮就是十几万 token 的固定开销。
- 分层记忆（chunks / events / links）已经上线并接管了**事实回忆**，memory.md 并不是唯一来源。
- 核心四节（人物底色 / 称呼关系 / 他的雷区 / 他的更正）**永不衰减**，这是红线。
- 她的人格连续性依赖这是**同一份**东西，不能变成"每次重新生成的人设"。

四种可选定位：

## 方案 A：人设契约（Constitution）——只留"她是谁"和"不能碰的线"

**做法**：memory.md 只保留四节核心 + 一段固定的说话风格说明，剥掉所有具体事实、偏好、近况；
事实类全部推给 chunks/events，靠召回注入。

- 优点：注入体量能压到 ~1.5 KB，最省；职责最纯粹，"改人设"和"记事情"彻底分开；衰减策略最干净（核心本就不衰减）。
- 缺点：**她会"不知道细节"**——如果召回没命中，像"椰果脆啵啵那杯奶茶"这种具体事就丢了，人味下降；
  召回质量从此直接决定她像不像本人，风险集中到一个点上。
- 适合：把召回质量再往上顶一档之后。

## 方案 B：分层文件（人设 / 长期偏好 / 近况三段，同文件不同区块）

**做法**：还是 memory.md，但内部明确分三段：`## 核心`（不衰减）、`## 长期`（月级慢衰减）、
`## 近况`（周级滚动覆盖）。注入时按段落分别取：核心全取，长期取摘要，近况只取最近 7 天。

- 优点：改动最小，一天内能上；token 可省 40–50%（近况段本来就是最长的）；仍然是"同一份文件"，连续性不破。
- 缺点：还是"一份文件多个角色"，段落边界靠约定维持，写着写着容易混（近况里塞进偏好）；
  衰减逻辑要写进代码，规则多了容易互相打架。
- 适合：想立刻省 token、又不想动架构。

## 方案 C：契约 + 白皮书分离（memory.md 做人设，facts.md 做事实索引）

**做法**：memory.md 只留人设与红线（同 A），另起一份 `facts.md` 做**人可读**的事实索引
（从 events 汇总生成，按主题分组，每天重建），注入时 facts.md 只取当前话题相关的几组。

- 优点：人设稳定、事实可重建（坏了重生成就行）；出问题时能一眼看出"这是人设问题还是事实问题"；
  人审阅方便——比翻 SQLite 舒服。
- 缺点：两套东西要对齐（events → facts.md 的汇总质量就是新的风险点）；多一次生成成本；
  重复信息可能出现（facts.md 和 chunks 说同一件事，注入时撞车）。
- 适合：想要可读、可人工审阅的事实层。

## 方案 D：完全体外化（memory.md 只剩指针，一切靠召回 + events）

**做法**：memory.md 缩到几百字节，只写"你是大肥鱼，其他全靠记忆"，事实与近况全部靠召回。

- 优点：理论上最省，架构最干净。
- 缺点：**人格连续性风险最高**——一次召回失败她就"失忆"，而且会显得健忘、反复问同一件事；
  与"不许忘"的红线冲突。不推荐。
- 适合：不推荐，仅列出对比。

## 我的建议

**先做 B，再做 A，C 视需要。** 理由：

1. B 是纯收益、低风险：今天就能落地，token 立省近半，不改任何调用方。
2. A 是终局形态，但它的前提是"召回够稳"——建议等 B 跑两周、看召回 miss 率再决定，
   否则会拿省钱换健忘。
3. C 的价值在"可读可审"，如果之后你想在网页端直接编辑她的事实记忆，C 才值得做。
4. D 不做：省下的 token 抵不上"她会忘"的代价。

落地顺序（B）：`memory-snapshot.ts` 里给三个段落打标记 → `memory-engine` 注入时按段落取 →
`jobs.ts` 每天滚动近况段 → 保留整份快照做回滚。整套最多两天。
