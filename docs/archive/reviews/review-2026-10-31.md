# 代码结构审查 · 2026-10-31

> 范围：`ds-memory` 引擎（84 个源文件 / 21,580 行，不含测试；77 个测试文件 / 881 用例全绿）。
> 目的：找出「结构上真正会拖累后续开发」的地方，给出可分批执行、每批都能独立回滚的方案。
> **本文只谈结构，不改行为**：记忆语义、外部 API 契约、线上数据一律不动。

---

## 一、结论先说

结构总体是健康的：模块按职责切得细、命名一致（`memory-*` / `emotion-*` / `relation-*`）、
纯函数与 IO 基本分离，测试覆盖同名文件。**问题集中在三个地方**：

| 位置 | 症状 | 后果 |
|---|---|---|
| `src/index.ts` | 2,293 行，一个文件同时装 97 条路由 + B 站 WBI 签名 + 静态资源透传 + cron 分发 | 改任意一条路由都要在 2,300 行里找；签名逻辑无法单测 |
| 关系/情绪领域 | 9 个 `emotion-*`/`affect-*`/`mood-*` + 5 个 `relation-*`/`attitude*` 文件，常量在 3–5 个文件里各定义一份 | 同一条规则（如 `RELATION_MAX`）要改多处，漏一处就是线上线下不一致 |
| 记忆领域 | legacy（`memory_entries`）与 next（`memory_chunks/facts/events`）两套索引并存，18 个文件 | 已知的 P2-2；切 `MEMORY_ENGINE=next` 前必须先收口 |

另外还有一批**低风险、机械性**的整洁项（死导出、重复常量、`console.log`），可以一次性做完。

## 二、P0：影响后续每一次改动

### P0-1 `index.ts` 需要按域拆分（2,293 行）

现状分布（行号来自当前 HEAD）：

```
  124–156   B 站 WBI 签名（BILI_MIXIN_TAB / biliSign / biliMixinKey）
  160–244   全局中间件（request-id、trace、鉴权旁路）
  245–440   /api/app/*：配对、心跳、记忆更正、定位、事件、client-messages
  441–790   health / day / balance / settings / login / chat / upload / tts
  790–1218  B 站与网页预览代理（web-preview、link-preview）、app 媒体、TTS 配置
 1218–1300  历史、图片、usage
 1300–2070  /api/admin/*（约 40 条：记忆、召回、成本、就绪度、情绪、统计、wipe-data）
 2072–2192  /api/proactive/*（队列、心跳、暂停、诊断）
 2193–2216  静态资源透传 + CHARACTER_NAME 替换 + no-store
 2218–2295  onError、context 刷新、cron 分发
```

**建议拆成：**

```
src/index.ts            装配：new Hono、中间件、挂 router、静态资源、cron 分发（目标 ≤ 250 行）
src/routes/app.ts       /api/app/*（设备侧）
src/routes/web.ts       health/day/balance/settings/login/chat/upload/history/image/usage
src/routes/tts.ts       tts 三组端点（任务队列、配置、speak）
src/routes/admin-memory.ts   /api/admin/memory/*（最大的一块，约 20 条）
src/routes/admin-ops.ts      /api/admin/{stats,cost,readiness,run-*,wipe-data,settings,test-mood}
src/routes/admin-affect.ts   /api/admin/{relation,affect/*,emotion/*}
src/routes/proactive.ts      /api/proactive/* + 手动触发/诊断
src/routes/bili.ts           B 站预览 + 网页 link-preview（含签名，可单测）
```

Hono 原生支持 `app.route('/api/admin', adminRouter)`，这是纯机械搬运；
**唯一要小心的是**：中间件顺序（`app.use('*')` 必须在挂 router 之前生效）、
`app.get('*')` 静态兜底必须最后挂、`openaiApp` 的挂载方式不变。

验收：`npx tsc --noEmit` + 881 用例 + 逐条 `curl` 打一遍关键端点（至少 health/day/chat 401/history 401）。
风险：中（路由顺序错了会 404）；可分批，一批一个 router。

### P0-2 关系数值的「单一真相」缺失

同一个概念散在多处：

| 概念 | 出现位置 |
|---|---|
| `RELATION_MAX = 1000` | `memory-maintenance.ts`、`relation-drivers.ts`、`relation-growth.ts` |
| `MOOD_MAX_DAILY_DELTA` | `attitude.ts`、`memory-maintenance.ts` |
| 5 轴默认值 | `memory-maintenance.ts`（AFFINITY_DEFAULT 等）+ `relation-facets.ts`（FACET_DEFAULTS） |
| 关系原型/阶段 | `attitude.ts`（STAGES 表）、`relation-facets.ts`（12 原型）、`attitude-policy.ts`（tone） |

**建议**：新建 `src/relation-model.ts` 只放常量与纯换算（上限、默认值、日增量帽、阶段阈值），
其余文件从它 import。**不动算法**，只搬常量。收益：以后调一个数值不用 grep 五个文件。

### P0-3 记忆两套索引并存（已知 P2-2）

`memory_entries`（legacy，关键词/向量/MMR）与 `memory_chunks/facts/events`（next）同时在线，
`resolveRecall` 里 legacy 与 next **串行**跑，共享 1,500ms deadline。
这意味着 shadow 模式下每条消息的召回延迟是「legacy + next」的和，而 legacy 这一半在切 next 后是纯浪费。

**建议**：把 `resolveRecall` 的 legacy 段做成「仅在 `mode !== 'next'` 时跑」——
现在就是这样，但 `shadow` 也跑 legacy 是为了对比数据；**切 next 后应立刻删 legacy 分支**，
并在 `pending-work.md` 里写明「删除条件 = MEMORY_ENGINE_* 全量切 next 满 7 天」。
