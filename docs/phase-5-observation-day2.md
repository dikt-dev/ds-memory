### D2-01 收到 AI 消息时跳一下/闪一下

现象：发送后等待回复，AI 消息出现时列表跳动/闪烁，不够丝滑。

已排查到的高概率结构原因：

- 列表是 `reverseLayout`，新 assistant 消息插入 index 0；
- `LaunchedEffect(itemCount)` 在新消息到达时执行 `scrollToItem(0)`，与插入/逐句展示同帧发生；
- `SegmentedMessage` 使用 `animateContentSize()`，消息内容逐句增长时高度变化；
- pending 删除和 assistant 插入由 Room 更新触发，可能出现两次布局变化。

修复方向：

1. 用户已在底部时，不额外 `scrollToItem(0)`；让 `reverseLayout` 自然保持 index 0；
2. 如果必须滚动，改为一次 `requestScrollToItem(0)` 或短动画，不在每次 itemCount 变化时立即跳；
3. 避免 pending 删除和 assistant 插入造成两个可见帧；
4. 对“逐句展示”的高度变化做稳定占位或关闭 `animateContentSize`；
5. 用 Macrobenchmark/FrameMetrics 验证 30 次回复无闪跳。

验收：连续 30 次回复，消息出现时无白闪、无上下跳；列表保持底部。

### D2-02 首次弹出/收起键盘卡顿

现象：每次打开 App 后第一次点输入框，键盘弹出和收起都一顿一顿；第二次之后明显好转。

当前判断：

- 不是媒体动画，优先怀疑 IME inset 动画 + 首次 Compose 布局/JIT；
- 现有 `imePadding()` 会让整个页面在键盘动画期间反复测量；
- 首次打开还会触发列表、输入框、阴影/模糊等首帧成本；
- 之前加的媒体预热只能覆盖 GIF/图片，不能覆盖 IME 布局。

修复方向：

1. 用 Macrobenchmark 记录首次 IME 打开/关闭的 frame timing；
2. 评估 `adjustResize` + `imePadding()` 是否重复触发 resize；
3. 对键盘高度做本地缓存，但只作为预热/占位，不替代系统动画；
4. 禁止在 IME 动画中做列表滚动；
5. 必要时改为 `adjustNothing` + 手动 inset 动画，或使用 `WindowInsetsAnimation` 统一驱动。

验收：首次弹出/收起键盘无持续掉帧；第二次与第一次体感一致。

### D2-03 AI 把六点下班说成五点

现象：用户说“下班了下班”，AI 回“五点了”，但记忆里是：

```text
深圳；8:15出门，8:30上班，18:00下班（下午六点，不是17:00/五点）。
```

已查到的对话：

```text
ID 785/789 assistant 曾说过“改到五点”“记得五点”
ID 790 user 说“下班下班”
ID 791 assistant 回“哟，五点了？”
```

说明不是记忆事实错误，而是模型把之前对话里的“五点”当成了下班时间，发生了上下文污染/自我引用。

修复方向：

1. 在记忆中明确写成“下班=18:00（下午六点），不是17:00”；
2. 提示词增加：作息时间以记忆中的明确事实为准，不引用聊天里临时约定的“五点”；
3. 清理代码/记忆里残留的 `17:00`、`五点下班` 表述；
4. 加回归用例：用户说“下班了”时，模型不能回答“五点了”；
5. 检查 `memory_entries`/`chunks`/`summaries` 是否还有旧时间。

验收：不同时间点连续问“我几点下班”，回答一致为 18:00；用户说“下班了”不出现“五点了”。

### D2-04 B 站链接先显示再发送

现象：发送 B 站链接时，App 先等预览解析，聊天记录没有立即出现；用户希望先完整显示本地消息/卡片，再处理发送给 AI。

修复方向：

1. 发送时先把原始文本和 URL 以本地 pending 消息插入列表；
2. 立即显示链接卡片骨架/占位；
3. 异步请求 `biliPreview`（标题、封面、摘要）；
4. 解析完成并更新卡片后，再把结构化资料发给 AI；
5. 解析失败保留原始链接消息，不阻塞发送。

验收：点击发送后本地消息立即出现；解析完成后卡片更新；AI 在卡片显示后才开始处理。

4. App 以文件/卡片形式展示；

验收：分享链接后 App 显示完整视频卡片；发给 AI 的是带摘要、字幕、抽帧说明的 MD。

### D2-06 动态/视频显示不出来或很慢

现象：发送动态后 App 很久才显示，视频大概率也不行。

修复方向：

1. 检查 `[GIF:key]` / `[视频:key]` 的解析和 `MediaBubble` 加载；
2. 上传后先用本地 URI 显示，再上传云端；
3. 本地缓存首帧/缩略图；
4. 失败显示错误占位和重试；
5. 确认 `/api/app/media` 路由和 R2 key 一致。

验收：发送后本地立即显示；网络慢时不阻塞本地气泡；失败有明确状态。

### D2-07 整体流畅度

现象：上下滑动聊天记录一顿一顿；每次重启 App 动画都要重新卡一次。

修复方向：

1. 用 Macrobenchmark 测滑动 jank、启动首帧、首次动画；
2. 减少每项阴影/模糊/`animateContentSize` 的过度绘制；
3. 图片/GIF 磁盘缓存 + 首帧缓存，限制并发解码；
4. 列表使用稳定 key、避免不必要的重组；
5. 启动时预热最近媒体，不预加载全部历史；
6. 如需更大缓存，提高 `MediaDiskCache` 上限并加 LRU 清理。

验收：滑动稳定 60fps；冷启动首次动画不重复卡顿。

### D2-08 定位功能

需求：收到定位后更改所在位置，每次更改写入记忆并记录原因。

设计方向：

1. App 申请定位权限，使用系统定位（FusedLocationProvider 或 LocationManager）；
2. 用户主动点击“更新位置”才上传，避免后台偷定位；
3. 服务端新增位置事实：

```text
当前位置=...
位置变更原因=...
更新时间=...
```

4. 写入 `memory.md` 的“关于用户/近期动态”，并通过 `/更正` 同级的记忆更新路径刷新 facts/chunks；
5. 记录变更历史，不只覆盖旧值。

验收：用户主动更新位置后，AI 下一轮能知道新位置和原因；未授权时不读取定位。
