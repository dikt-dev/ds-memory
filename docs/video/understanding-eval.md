# 视频理解方案评估（2026-10-30）

> 结论先说：**两条主流路线里，索引化对我们是过度设计，主动探索有可行性但要收敛到「单跳回看」。**
> 真正卡准确率的不是帧数，而是**我们现在把字幕的时间戳扔了**。

## 1. 我们的场景和论文里的场景不一样

| 维度 | 典型视频问答 | 我们 |
|---|---|---|
| 视频量 | 语料库，反复查询 | 一次一条，聊完就过 |
| 目标 | 答对问题 | 像看过一样地反应，且不能编 |
| 指标 | Video-MME 准确率 | 用户观感：说得对不对、像不像看过 |
| 计算位置 | GPU 服务器 | 手机端（Worker 无 ffmpeg、无 GPU） |
| 预算 | 每题 $0.0067 | 每条视频现有成本 ≈ ¥0.001（1 张图 + 文本） |

所以那组「videoctx 83.3% vs Gemini Flash 53.3%」的数字不能直接搬——它衡量的是给定问题答对的比例，
我们衡量的是「蓝大小姐看完视频的反应像不像真的看了」。**这两个指标对帧的要求方向不同**：
前者要定位到与问题相关的那几帧，后者要避免说错任何一句、并且有画面感。

## 2. 逐条评估

### 路径一：Agentic 主动探索 —— 可做，但要砍成「单跳」

我们有的东西：模型支持多图、App 已经能下载 mp4（≤30MB，`MediaMetadataRetriever` 可任意 seek）、
B 站给全量字幕。所以「模型说要看 01:12，App 抽那一帧再问一轮」这件事**完全做得出来**。

做不到的是原生工具调用循环（Video-o3 那种多轮自主规划）：DeepSeek 没有视频工具接口，
Worker 里也没有 ffmpeg。要在我们这儿实现，得自己在 App 端写编排，成本不在模型、在**每次多一轮往返**：

```
现状：1 次请求 → 宫格 + 字幕 → 回复        （约 3-5s）
单跳回看：1 次请求 → 模型给出 ≤3 个时间点 → App 抽帧 → 第 2 次请求 → 回复（约 6-9s）
```

**可行性：高。** 前提是 mp4 留在手机上（现在 30MB 上限、缓存在 cache 目录，够用）。
**代价：** 每条视频多一次模型调用（约 +¥0.001、+3s）。
**建议：** 只在「字幕缺失」或「用户问的是画面细节」时才触发，不做成默认路径。

### 路径二：索引化 + 检索 —— 不划算

它成立的前提是「同一条视频会被反复问」。我们的现实是一次一条、看完就过，索引建完就废了。
而且整条流水线里我们缺三样：

| 环节 | 我们有没有 |
|---|---|
| 场景分割（PySceneDetect/TransNetV2） | ❌ 手机上要自己实现帧差聚类 |
| 逐场景 VLM 描述 | ⚠️ 能做，但每条视频要多花 3-10 次调用 |
| 语音对齐（Whisper） | ✅ **不需要**——B 站直接给字幕，比 ASR 准 |
| 向量索引 | ✅ 有（D1 + bge-m3），但那是给长期记忆用的 |

**可行性：中。值得做的前提是出现「同一条视频追问第二次」的真实需求。** 现在没有。

## 3. 真正该先修的一件事：字幕的时间戳被扔了

`ApiClient.kt:640` 现在只取 `content`：

```kotlin
val lines = (0 until body.length()).map { body.optJSONObject(it).optString("content").trim() }
subtitle = lines.joinToString("\n")   // from / to 全丢了
```

结果：模型手上有「宫格每格的秒数」和「一段没有时间的台词」，**两者对不上**。
它只能整体感觉「大概是讲这个」，回答里就容易张冠李戴——这正是你说的「看不太准」。

改成带时间戳：

```text
00:03 在吗嗯嗯嗯嗯嗯嗯啊
00:06 别杀我
00:08 我有白米饭都给你
```

模型立刻能做出三件事：

1. 某格画面 00:12 时，把台词对齐到那一格；
2. 字幕有空档（比如 00:20–00:30 没台词）时，知道那段是纯画面，重点看画面；
3. 回答里引用时间更准（「中间那段」→「二十几秒那块」）。

**成本：30 分钟，改 3 行。这是目前性价比最高的一步，比任何索引方案都直接。**

## 4. 建议的推进顺序

| 优先级 | 事项 | 工期 | 风险 |
|---|---|---|---|
| P0 | 字幕带时间戳 | 30 分钟 | 极低，只是多传文本 |
| P0 | 提示词分工：台词以字幕为准，画面只补视觉细节，不拿画面推断台词 | 30 分钟 | 低 |
| P1 | 宫格分辨率与竖屏布局（**已完成**，`7cc71e2`） | — | — |
| P2 | 单跳回看：模型可要求 ≤3 个时间点，App 抽帧补一轮 | 1 天 | 中（多一次往返，要防死循环） |
| P3 | 场景索引 | 暂缓 | 需先出现重复提问的真实需求 |

## 5. 对文中几个论断的核对

- 「不要忽略音频轨」：对我们**不成立**——B 站字幕已经覆盖台词；但**声音事件**（摔门、笑声、BGM 突然停）确实丢了，
  这类信息只能靠画面或 ASR 之外的音频分析，暂时不做。
- 「关键帧要跟问题相关，而不是均匀分布」：对，但我们的问题往往不是具体提问，而是「你看了觉得怎样」，
  没有明确的检索目标 → 均匀抽样反而合理。**等支持追问了再谈相关性选帧。**
- 「计数、动作顺序最容易错」：认同，且这两类恰好是字幕帮不上、宫格又看不清的。如果用户真问「他开门了几次」，
  只能走单跳回看。

## 6. 一句话

我们现在缺的不是「更多帧」，是**让已有的 6-9 帧和时间对上**。先花半小时把字幕时间戳接上，
准确性提升会比再加一排格子明显；主动探索等有追问需求时再上，索引化暂时不做。
