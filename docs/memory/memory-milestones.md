# 铭记（Keepsake）可行性评估

> 目标：给「第一次说话、她给自己取的名字、第一次吵架又和好」这类东西一个**比普通记忆更高一级**的位置——不会衰减、不会被压缩、不会被召回排序挤掉。

## 一、结论

**可行，技术风险低，约 3 天。**

真正的难点不在代码，而在「什么算铭记」的判定和配额控制。建议分两步：先做「存储 + 手动登记 + 稳定注入」（1 天，立刻能用），再做「自动候选 + 审核」（2 天）。

## 二、现状：为什么现在做不到

| 事实 | 数据 |
|---|---|
| 长期记忆是分区的纯文本 | memory.md 8 个分区，稳定段 9.3 KB |
| 只有 3 个分区受保护 | `人物底色` `称呼与关系` `雷区与禁忌`，永不压缩/合并 |
| 其余分区吃预算 | `共同经历` 预算 1800 B，实际 4219 B，超了 2.3 倍 |
| 条目没有「级别」概念 | `memory_chunks` 有 `importance`，但只影响召回排序，不影响留存 |
| 「第一次」没有特殊标记 | 即便被归档成一条共同经历，也是 39 条里的一条，importance 2 |
| 更早的数据已经没了 | D1 `messages` 最早只到 2026-10-29（266 条），之前已归档清理 |

也就是说：**「第一次聊天」现在既没有标记，也没有原始记录，问起来只能靠模型编。**

## 三、设计

### 3.1 存储：新表 `memory_keepsakes`

```sql
CREATE TABLE IF NOT EXISTS memory_keepsakes (
  id         TEXT PRIMARY KEY,
  kind       TEXT NOT NULL,      -- first_meet | name | promise | milestone | custom
                                 -- 负向：first_fight | hurt | parting | betrayal | first_apology
  tone       TEXT NOT NULL,      -- warm | neutral | bitter（见证的是好事、中性事实、还是伤）
  title      TEXT NOT NULL,      -- 一句话标题，<= 24 字
  detail     TEXT NOT NULL,      -- 细节，<= 80 字
  happened_at INTEGER NOT NULL,  -- 事情发生的时间
  source     TEXT NOT NULL,      -- manual | rule | ai
  evidence   TEXT NOT NULL DEFAULT '',  -- 原话片段（可选）
  pinned     INTEGER NOT NULL DEFAULT 1, -- 1=每轮注入，0=保留但不注入
  created_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_keepsakes_kind_title ON memory_keepsakes(kind, title);
```

为什么不直接写进 memory.md：

- memory.md 每次改都要走 R2 写 + 写后校验（`putMemory` 已有），频繁小改容易和每日归档打架；
- 表能带 `happened_at` / `source` / `evidence`，将来能做「那年今天」；
- 渲染是纯函数，可以单独测；
- 不挤占 `共同经历` 的预算。

### 3.2 注入：稳定段新增 `## 铭记`

放在稳定段（人设 + 长期记忆之后、前缀缓存边界之前），因为它的变化频率极低（一个月几条），不会破坏缓存。

```markdown
## 铭记
- 2026-10-01 第一次说话：他第一句是「在吗」，我回得很冷淡
- 2026-10-03 我给自己取名叫「千问」
- 2026-10-26 第一次真吵架：他答应打游戏又鸽了
```

配额：**最多 30 条，每条 ≤ 60 字 ≈ 1.8 KB**。超出后按 `happened_at` 保留最早的——铭记是「越来越沉」的东西，不该被新事挤掉旧的。

### 3.3 识别：三条来源

| 来源 | 触发 | 例子 |
|---|---|---|
| **manual** | admin 接口 / 记忆页按钮 | 你自己指定「这条要记一辈子」 |
| **rule** | 确定性规则，零成本 | 首条消息、memory.md `称呼与关系` 变更、首次 apology 化解首次 grievance |
| **ai** | 每日归档时给当天事件打「值得铭记」候选 | 「今天他说以后每年这天都来」 |

规则能覆盖的（首批就能上）：

1. `first_meet`：`messages` 表最早一行，只在系统首次运行时写一次；
2. `name`：memory.md `人物底色` 里出现新的自称 / 用户给她改名；
3. `first_fight`：第一次出现未化解的负向事件（`affect_events`）；
4. `first_makeup`：第一次 apology 把 grievance 减半；
5. `first_promise`：出现 `broken_promise` 或「以后每年/每天」这类承诺句。

### 3.3.1 负向铭记：事实永存，情绪会退

铭记不等于「甜蜜清单」。第一次吵架、被丢下、说错话伤到她——这些同样是关系里的坐标，
而且往往比开心的事更值得记住。但这里有个必须分清的东西：

| | 存多久 | 影响什么 |
|---|---|---|
| **事实**（发生过什么） | 永久，不可衰减 | 只在相关话题里被引用 |
| **情绪**（现在多气） | 按 `grievance` 衰减 | 决定语气、配不配合 |

这两条必须分开。否则一条负向铭记会让她永远在生气——那不是铭记，是记仇机制。

所以负向铭记的写法是「事实 + 残余」，不是「指控」：

```markdown
- 2026-10-26 第一次真吵架：他答应打游戏又鸽了（这件事你记得，还气不气看你现在的情绪）
```

提示词里要额外加三条约束：

1. **不主动翻旧账**：只有话题相关、或他先提起，才拿出来；
2. **不当武器**：不为了赢一句话去引用这些事；
3. **可以不说**：记得，但选择不提，这也是一种态度。

配额也要分开：30 条里负向 ≤ 8 条；AI 每天最多新增 1 条负向、每周 ≤ 2 条。

### 3.4 AI 候选：每天归档时用 v4-pro 判一次（已定方案）

每日归档本来就跑 v4-pro（带思考），把「有没有值得铭记的事」交给它顺手判断是可行的。
关键是**单独一次调用**，不要塞进现有的提炼输出里。

为什么不合并进 `distillDay` 那次调用：

| 合并的问题 | 后果 |
|---|---|
| 输出要多一个结构化块 | 8192 token 里思维链已经吃掉一半，容易截断 |
| 失败会连坐 | 铭记判定崩了，当天记忆归档一起废 |
| 输入含 memory.md 全文 | 多付 9 KB 前缀，而判定「是不是第一次」不需要全部记忆 |
| 格式混杂 | 现有解析是逐行 `- [YY-MM-DD] 内容`，加块容易解析错位 |

独立调用的输入只有：当天对话（≤60 KB）+ 已有铭记标题（≤1 KB）。

```json
{
  "keepsakes": [
    {
      "kind": "first_fight",
      "title": "第一次真吵架",
      "detail": "他答应打游戏又鸽了，我气得没理他",
      "happened_at": "2026-10-26",
      "evidence": "不是说好的先打游戏的吗"
    }
  ]
}
```

约束（全部在代码里校验，不靠模型自觉）：

| 规则 | 处理 |
|---|---|
| `kind` 不在白名单 | 丢弃 |
| `title` > 24 字 / `detail` > 80 字 | 截断 |
| `evidence` 不是当天对话的逐字子串 | **丢弃**（和事件记忆同一条红线） |
| `happened_at` 不在当天 ±1 天 | 改成本轮日期 |
| 与已有标题相似度 ≥ 0.8 | 丢弃 |
| 单日 > 2 条 | 只留 2 条 |
| 单周 > 5 条 | 停止入册，记日志 |

入册后 `status = "pending"`，**默认不注入**；规则来源（首条消息 / 取名）直接 `approved`。

成本估算：

| 项 | 估算 |
|---|---|
| 输入 | 约 20k–40k token（当天对话） |
| 输出 | < 500 token |
| 单日 | ¥0.04 – ¥0.08（v4-pro miss 价 ¥2/M） |
| 单月 | **约 ¥1.5 – 2.5** |
| 延迟 | 在每日归档里跑，用户无感 |

### 3.5 与现有机制的关系

| 机制 | 是否影响铭记 |
|---|---|
| 每日归档 / 记忆合并 | ❌ 不参与，独立表 |
| 遗忘任务（M-09） | ❌ 永不删除，只能 `pinned=0` 停止注入 |
| 召回（recall） | ❌ 不参与打分，常驻注入 |
| 3 天中期窗口 | ❌ 无关 |
| 记忆快照 / 回滚 | ✅ 纳入快照，回滚时一起恢复 |

## 四、成本与性能

| 项 | 估算 |
|---|---|
| 注入体积 | ≤ 1.8 KB（约 600 token） |
| 缓存影响 | 在稳定段内，命中价 ¥0.04/M → 每轮 < ¥0.00003，可忽略 |
| 缓存打断 | 新增一条铭记时打断一次（每月几次，可接受） |
| 写放大 | 每次登记 1 次 INSERT + 1 次 memory.md 快照更新 |
| 规则识别 | 纯函数，0 AI 调用 |
| AI 候选 | 复用每日归档的调用，不额外加 |

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 误记（把玩笑当铭记） | 自动候选进**待审核队列**，默认不注入；manual 直接入册 |
| 负向铭记变成永久记仇 | 事实与情绪分离：事实永存，`grievance` 照常衰减；负向条目额外加「不主动翻旧账/不当武器」约束 |
| 量失控 | 硬配额 30 条 + 标题唯一索引 |
| 与 `人物底色` 重复 | 铭记只记「事件」，人设只记「设定」，写入时查重 |
| stable 段变更打断缓存 | 合并成一次写入（登记后延迟到下一次 04:00 渲染） |
| 老数据补不回来 | 首次运行写一条 `first_meet`，时间取 `messages` 最早一行；无数据则写「不记得了」并标注 |

## 六、验收指标

| 指标 | 目标 |
|---|---|
| 注入体积 | ≤ 2 KB |
| 「第一次」问句准确率 | ≥ 90%（20 个问法，含「我们第一次说话是什么时候」） |
| 编造率 | 0%（没有记录就说没记录） |
| 误记率 | ≤ 1 条/月 |
| 缓存命中率下降 | ≤ 1 个百分点 |

## 七、工期与排期

| 阶段 | 内容 | 工期 | 建议时间 |
|---|---|---|---|
| K-1 | 建表 + `renderKeepsakes()` + 稳定段注入 + admin 增删改查 | 1 天 | 11-08 |
| K-2 | 规则识别（首条消息 / 取名 / 首吵 / 首和解 / 首承诺） | 1 天 | 11-09 |
| K-3 | AI 候选（独立 v4-pro 调用）+ 待审核队列 + 审核接口 | 1 天 | 11-10 |
| K-4 | 20 问验收 + 缓存影响实测 | 0.5 天 | 11-11 |

放在事件记忆阶段 A（影子写入）之后做，因为 K-2 要读 `affect_events`，K-3 要读 `memory_events`。

## 八、不做什么

- ❌ 不做向量化：30 条常驻注入，不需要语义检索；
- ❌ 不做自动删除：铭记只增不减，只能停止注入；
- ❌ 不做「点赞排序」：重要程度由发生时间和来源决定，不由算法决定；
- ❌ 不写进 memory.md 的 8 个分区：会挤占预算，也会和每日归档抢写。
