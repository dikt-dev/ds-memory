# 记忆系统 v2 设计：事件级记忆

> 前提：**不计 token、不计延迟**。聊天不是实时系统，等 1–2 秒换准确率是划算的。
> 因此这里唯一的约束不是钱，而是三个物理限制：上下文窗口、注意力分布、冲突干扰。

日期：2026-10-30　状态：设计稿，未实施

---

## 0. 一句话

**记忆的单位从「一句话事实」变成「事件」；事件同时保存摘索引和原文指针；检索取事件，注入原文。**

现在的链路是：

```text
原文 → 蒸馏成一句话 → 存 memory.md / memory_chunks → 召回那句话 → 注入
```

细节在蒸馏那一步就永久丢失了。改成：

```text
原文（永久保留） → 切事件 → 事件(标题+摘要+关键引文+原文指针) → 召回事件 → 展开原文 → 注入
```

摘要只负责「找得到」，原文负责「答得准」。

---

## 1. 为什么不能把全部原文塞进去

| 限制 | 数值 | 后果 |
|---|---|---|
| 上下文窗口 | 128k ≈ 90k 汉字 | 三个月聊天约百万字，塞不进 |
| Lost in the middle | 中间位置利用率明显低于首尾 | 塞进去也用不上 |
| 冲突干扰 | 新旧事实同时在场 | 模型摇摆，答对率反而降 |

经验甜点区：**单次注入 20k–40k 字符**。超过后继续加内容，准确率开始下降。

所以「不计 token」的正确解读是：**不为了省字而牺牲信息，但也不做无效堆砌**。

## 2. 数据模型

### 2.1 事件表 `memory_events`

```sql
CREATE TABLE memory_events (
  id            INTEGER PRIMARY KEY,
  date_key      TEXT NOT NULL,            -- 26-10-26
  started_ms    INTEGER NOT NULL,
  ended_ms      INTEGER NOT NULL,
  title         TEXT NOT NULL,            -- ≤20 字，检索与展示用
  summary       TEXT NOT NULL,            -- ≤120 字，注入用
  quotes        TEXT NOT NULL,            -- JSON 数组：1–3 条原句（verbatim）
  msg_ids       TEXT NOT NULL,            -- JSON 数组：本次事件的原始消息 id
  entities      TEXT NOT NULL,            -- JSON：人物/项目/地点/偏好 标签
  emotion       TEXT,                     -- 可选：当次情绪基调
  importance    INTEGER NOT NULL DEFAULT 3,
  status        TEXT NOT NULL DEFAULT "active",  -- active | superseded | closed
  superseded_by INTEGER,                  -- 改口链：指向取代它的事件
  vec_summary   BLOB,                     -- 事件摘要向量
  vec_quote     BLOB,                     -- 关键引文向量
  created_at    INTEGER NOT NULL
);
CREATE INDEX idx_events_date ON memory_events(date_key);
CREATE INDEX idx_events_status ON memory_events(status);
```

### 2.2 事实表（复用 `memory_facts`）

事实是事件的**结论投影**，用于快速回答「他喜欢什么」。每个事实记 `event_id`，冲突时不删除，改 `superseded_by`。

### 2.3 原文

不新增存储：继续用现有的 `chat_logs/YYYY-MM-DD.log` 与月归档。事件只保存 `msg_ids`，取原文时按 id 回查（D1 或归档）。

## 3. 写入流程（离线、可重跑）

触发：每天 04:00 归档后；或每累计 40 条消息。

```text
1. 取未处理的消息区间 [last_event_end, now]
2. 切分事件：
   a. 时间间隔 > 45 分钟 → 强制切
   b. 否则交给模型判断「话题是否转移」
3. 每个事件产出：
   - title（≤20 字）
   - summary（≤120 字，写「发生了什么 + 结论」）
   - quotes（1–3 条原句，逐字摘录，不改写）
   - entities（人物/项目/地点/偏好）
   - facts（0–3 条，每条 ≤30 字）
4. 冲突检测：新 fact 与旧 fact 语义冲突 → 旧 fact 标 superseded，链到新事件
5. 幂等：以 (started_ms, ended_ms) 为键，重跑覆盖同一区间
```

**关键约束：quotes 必须逐字来自原文**，模型只做挑选不做改写。这是「记得准」的根基。

## 4. 读取流程（每轮）

```text
1. 构造查询
   - 当前消息
   - 最近 6 轮原文（提供指代上下文）
   → 生成 2–3 个子查询：实体查询 / 时间查询 / 意图查询

2. 粗召回（各取 top 20，合并去重）
   - 全文 BM25：事件 title + summary + quotes
   - 向量：vec_summary、vec_quote 各一次
   - 实体精确匹配：entities 命中加权

3. 重排（多因子加权）
   score = 0.45·相关度 + 0.25·时间新近 + 0.20·重要性 + 0.10·状态
   状态：active 全分，superseded 打 0.5，closed 打 0.6

4. 展开（取 top 8 事件）
   - summary
   - quotes（逐字）
   - 原文邻域：msg_ids 前后各 2 条
   去重后按时间排序

5. 注入布局（对抗 lost in the middle）
   - 最相关的 3 个事件放在**最靠近用户消息**的位置
   - 其余按时间放在前部
   - 总预算 8k–12k 字符，超出时先丢「只命中关键词、无引文」的事件
```

## 5. 注入格式

```text
## 相关往事（按时间）

[26-10-26 21:14] 想学剪辑
他说那个 B 站视频剪得好，想学；她提醒他连剪映都没装。他说明天就下。
原话：
  用户：那个视频剪得挺好，我也想学
  她：你连剪映都没打开过吧
  用户：真的，我明天就下

[26-10-29 10:02] 改口：暂时不学了
原话：
  用户：算了，最近太忙，剪辑先放着
```

**规则（写进提示词）**：

| 规则 | 说明 |
|---|---|
| 引用往事就带日期 | 「你 26 号说过想学剪辑」 |
| 新旧冲突时用新的，并说明改口 | 不要装作一直如此 |
| 只有摘要没有原话时 | 可以概括，不要编造细节 |
| 什么都没检索到 | 说没印象，不猜 |

## 6. 分层不变的部分

| 层 | 内容 | 变化 |
|---|---|---|
| 短期 | 会话内全部原文 | **不变**（已实现，只追加不滑窗） |
| 中期 | 最近 3 天 | 由「一句话条目」升级为「事件摘要 + 引文」 |
| 长期 | memory.md | 保留，但降级为「索引 + 人设快照」，不再是唯一事实来源 |

memory.md 仍然重要：它是稳定前缀（缓存友好）和人物底色的载体。真正的事实检索走事件库。

## 7. 记忆维护（每天一次，离线）

| 任务 | 内容 |
|---|---|
| 近重复合并 | 同一件事被切成两个事件的合并，保留较多引文的那个 |
| 改口链收敛 | 同一主题连续 3 次改口时，合并为「演变」事件，保留首末 |
| 长期未提及 | 90 天内从未被召回且 importance ≤2 的事件，降权不删除 |
| 用户纠正 | 用户说「不是这样/记错了」时，标记事件为 `wrong`，生成更正事件 |

**永远不物理删除**：只改状态与权重。

## 8. 验收

### 8.1 需要先建一个测试集

50 条历史问题，每条标注：

| 字段 | 说明 |
|---|---|
| 问题 | 「我上次说的那个剪辑的事后来怎么样了」 |
| 期望要点 | 想学剪辑 → 后来太忙先放着 |
| 来源消息 id | 用于判定是否答对来源 |
| 干扰项 | 同话题但不同时间的错误答案 |

### 8.2 指标

| 指标 | 目标 |
|---|---|
| 要点命中率 | ≥85% |
| 时间引用准确率 | ≥90%（引用的日期必须真实存在于来源） |
| 改口一致性 | 100%（不许把旧事实说成仍然有效） |
| 编造率 | 0%（出现不存在的人名/数字即失败） |
| 无效注入率 | 注入的往事中被判「无关」的比例 ≤15% |

### 8.3 A/B

同一批问题跑旧链路（现状）与新链路，人工盲评 30 条，新链路胜率 ≥70% 才算通过。

## 9. 迁移

| 步骤 | 内容 | 可逆 |
|---|---|---|
| 1 | 建表，先只写不读（影子模式） | 是（不读即无影响） |
| 2 | backfill 最近 30 天事件（从归档原文重建） | 是 |
| 3 | 读路径灰度：按渠道（app/web）分别开关 | 是 |
| 4 | 对比验收指标后全量 | 是 |
| 5 | memory.md 改为只保留人设 + 索引 | 需备份快照 |

回滚：读路径一个开关回到旧链路，事件表留着不读即可。

## 10. 分阶段实施

| 阶段 | 内容 | 产出 |
|---|---|---|
| A | 事件表 + 写入流水线（影子） | 有数据、不读 |
| B | 读路径：粗召回 + 重排 + 原文展开 | 新召回链路，可开关 |
| C | 注入布局 + 提示词规则 | 回答质量变化 |
| D | 维护任务（合并/改口/降权）+ 测试集 | 可长期运行 |

建议顺序：**A → B → 验收 → C → D**。B 结束就能看到效果，C/D 是打磨。

---

## 11. 明确不做

| 不做 | 原因 |
|---|---|
| 把全部历史拼进上下文 | 塞不进，且中间位置失效 |
| 用摘要替换原文 | 已经在丢细节，不能继续 |
| 物理删除旧记忆 | 关系型产品的信任底线 |
| 为了省 token 砍记忆 | 本轮前提明确不计成本 |

## 12. 与现有实现的衔接

| 现有 | 处理 |
|---|---|
| `memory_chunks`（一句话事实 + 向量） | 保留作快速索引；新增事件向量并行 |
| `memory.md` | 保留为稳定前缀与人设载体 |
| 短期会话记忆（只追加） | 不动 |
| 中期 3 天条目 | 升级为事件摘要 + 引文 |
| `resolveRecall` / `expandLinkedChunks` | 由新读路径替换，保留旧实现做回滚 |
